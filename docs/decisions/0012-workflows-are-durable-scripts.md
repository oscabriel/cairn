# Workflows are durable scripts on pi-durable

The model writes a workflow as a JavaScript program run in pi-codemode's deterministic QuickJS sandbox. Its tools (`agent`, `stone`, `verify`, `integrate`, `approve`) are durable nested tool tasks, so a crashed workflow resumes from its journal. Fan-out is `Promise.all`: code mode runs a script's calls concurrently and journals each result, so there is no `parallel` tool.

Scripts fail when their deadline passes or a replay diverges. The workflow sandbox therefore has no deadline (`timeoutMs: Infinity`; the default is 300 s including time in tools), and Cairn refuses a script's own `timeout_ms`. Every node is a replay-safe tool that finds its earlier work after a restart: a subagent by its owning task, a submission by its request ID, an approval by its record (ADR 0013), and long work by a durable handle to a process outside the brain, which an abort ends.

Gate S3: a four-node workflow survives `kill -9` of the brain mid fan-out with no node rerun and no result lost, with one node waiting on an approval and one running longer than 15 minutes. Passed on 2026-10-21; measured in `spikes/3-workflows/NOTES.md`.

On pi-durable 1.4.0 (rerun 2026-10-22), five crashes in a row during a node's wait park the workflow's waiting tasks; a retry resumes them with no node rerun. Clean stops don't count, because the brain closes the Harness on SIGTERM. The UI shows parked tasks with a retry.

Amended for phase 2 (decided 2026-10-27, `docs/phase-2/notes/workflows.md`; gated with phase 2's workflow judges). A single node may be stopped: it is replay-safe, measured across five `kill -9` cases including one between the abort mark and the node seeing it, and the script sees `null` for that node. Workflows get their own pool of script slots, because a workflow holds its slot for its whole run and code mode's four shared slots would block other threads. Workflow scripts carry a fixed prelude (`agent`, `parallel`, `pipeline`, `phase`, `log`, `budget` over the node tools), injected by a `beforeTool` hook that also strips `export const meta`; `parallel` stays a prelude function, not a tool. pi-codemode replays `Date.now()` and `Math.random()` from its journal and a seed, so they are allowed in scripts. A workflow runs inside the run of the thread that launched it in phase 2; a coordinator thread of its own is a later spike. A pi version change kills running workflows, so the deploy refuses one while a workflow runs.

Gate evidence for the amendment (package 4D, 2026-10-29): `judges/workflow-kill.sh` on a judge brain (a pi-durable Harness over SQLite with Cairn's code mode, the workflows extension and its gate, and the results extension, over faux models) passed 16 of 16 cases and its control failed rightly. The kill matrix carries spike 3's cases onto the real node tools and ledger (plain, kill mid fan-out, kill before the nodes, three kills, a kill between a node's reserve and its submit, a kill inside its settle, a kill between Go and the codemode call, the prelude's rewrite stored and replayed, a kill while the script's question waits, and a pi bump between lives that ends the call `replay_diverged`); every node was dispatched once, with one child per row and every row naming the accepted launch approval. The stop matrix is the probe's five cases on the real `agent` tool plus stopping the last node: the stopped node was `null` to the script, its work never finished, its row `stopped`, and nothing reran across `kill -9`. The control (a dispatch that ignores its row) dispatched three nodes twice. The ledger conformance suite (`WorkflowLedger.test.ts`, 20 scenarios on pi-durable) holds the gate and the envelope: an unapproved or edited script, a forged `workflow_begin`, a pasted prelude and a model-written `tools.agent` call are refused with nothing dispatched, and a node outside the envelope or past its cap is a refused row the script sees as `null`; with the caller check removed, the forged and pasted cases fail. Workflow scripts take their slots from an eight-slot pool of their own (`WorkflowSlots.test.ts`: two workflows filling theirs leave code mode free, and the control with one shared pool makes it wait).

Stop for the amendment (package 5C, 2026-10-29). A user stops one node with `workflow.stopNode` and a whole workflow with `workflow.stop` (`WorkflowStop.ts`); both are idempotent and answer once the abort mark is committed, waiting at most 10 seconds for the task to end. A whole-workflow stop aborts the script call, so its running nodes stop, settled results stay and the row ends `stopped` with `partial: stopped`; an approved workflow whose `codemode` call has not come yet is ended in one commit, and the gate then refuses its script. A proposed one is refused with Conflict: its launch card's Decline ends it. A stopped node keeps a receipt of what its child used, so its spend still counts against the budget. Every node tool polls the stop: its waits end at the abort signal (`untilStopped`) and it checks between steps, because `abortTask` waits for the tool's invocation to end. Gate evidence: `judges/workflow-stop.sh` (the node stop matrix, every stop through the RPCs' service) passed 12 of 12 cases and its control failed rightly: the probe's five cases, stopping the last node, stop-then-budget (the stopped node's receipt and the script's budget reading hold its spend), a node held 6 seconds in a wait deaf to its signal stopped in 3 ms, a whole-workflow stop with and without a `kill -9` before it and inside a deaf child's window, and a stop between Go and the `codemode` call (nothing dispatched). Each stopped node was `null` to the script where the script went on, its work never finished, and nothing reran across a kill. The control (node tools deaf to the stop) took 5.7 seconds to stop the held node. `WorkflowStop.test.ts` holds the same rules in process, and its receipt check fails with the stopped node's receipt removed.
