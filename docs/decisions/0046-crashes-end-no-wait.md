# Crashes end no wait

pi-durable 1.5.0 removed park and retry. A task a crash cuts off `restartLimit` times in a row without committing a new state now ends: a tool call with a `restart_limit` error result, an extension's task `faulted`. Cairn's approvals (ADR 0013), a subagent's start (ADR 0030), its reporters and a workflow's watchers (ADR 0012) waited across crashes by being parked at the fifth and retried at boot. On 1.5 the same five crashes would end a pending approval's call, and the user's answer would find nothing to run, against gate S4.

The preferred design moved each wait off its running invocation: a task asleep on pi-durable's clock until its record settles or expires, which a crash does not count. pi-durable 1.5.1 cannot express that for a tool call. Only a task's own committed state (a checkpoint, a `waiting` on tasks, a `sleeping`, an outcome) is progress, and a tool's `execute` commits none of these: the `pi.tool` task's checkpoint stays `{ phase: "execute" }` on every rerun, and a tool has no `sleepUntil` or durable wait (its `waitForTask` waits in memory, so the tool task stays `running` and is counted). Every Cairn wait on a person is a tool call (a gated call, `ask_user`, `ask_parent`, a brief's spawn, a workflow's question), so ending the call and answering by a later input would change what the model sees in every one of them. Cairn's own task kinds can already sleep (a brief's expiry does), but they are not where S4 breaks.

So the brain opens its Harness with `restartLimit` infinite (`apps/server/src/brain/RestartLimit.ts`) and does its own crash accounting at boot (`CrashLimit.ts`, the `crash limit` repair, after open and before resume). A live task cut off five times in a row is aborted, unless it is a wait Cairn keeps however often the brain dies:

- a tool call that waits: one that holds a record of its own in its conversation's `cairn.approvals` (`call-<task id>`, whatever its status: a gated call, `ask_user`, `ask_parent`, `workflow_plan`, a workflow's `approve`, `agent` and `verify` nodes, an Executor or portal call that asked), a workflow's script call (its row's `codemodeTaskId`), or a call of `subagent_status`, which waits on its children with no record; and every tool call a kept call is nested under, so a code mode script is not ended while a call it made waits. A kept call reruns only to wait again or to read its decision, and a gated call's effect runs at most once by its effect mark;
- the subagent tasks that wait (the brief and its tell sleep, the reporter waits on its child, the start makes a Go'd child once) and a workflow's watcher and budget stopper.

What boot ends is work that may itself be what crashes the brain: a tool call that waits on nothing (a replay-safe read, search or script the brain keeps dying in ends with the "Tool <name> was aborted" result the model reads, and the turn goes on), a generation (pi-durable already charges a request a crash cut off as a failed attempt under the retry policy), a compaction, and Cairn's other task kinds. An ended generation or compaction ends as a stop does: the run ends `interrupted`, the thread row goes idle with no error, and only the `boot_crash_limit` log line says crashes ended it. A run pi-durable itself ends for a crash (a request cut off with no retry left, reason `interrupted`) is the failure class `brain_restart`, and the row says "The brain restarted while the model was answering. Send again to retry."

Removed with park: `Parked`, `TaskParked`, the seam's `retry`, `thread.retryTask`, the `parked` thread activity and `parkedTaskIds` on the wire, the Retry banner, and the three boot retries; migration `0015_ParkedRemoved` rewrites a row a 1.4 brain stored as `parked` to `idle`, which the boot reconcile then sets from the brain.

What this gives up. A tool call that holds a record and whose rerun after its decision crashes the brain loops forever (no Cairn tool does in-process work after an answer that is not marked or idempotent); so does an abort handler that crashes the brain, since an abort mark starts pi-durable's count over and boot cannot end a task twice. A subagent's start that crashes the brain loops too, where ADR 0030 wanted a human Retry: no retry exists on 1.5, and the review fixes of 2026-11-09 hold a Go'd brief's start to the same promise as an approval, to run once however often the brain dies. The accounting runs once per process boot: a Session the brain's supervisor reopens after a storage failure, in the same process, resumes without it, so a task whose commits fail the Session every time reruns at each reopen for as long as the process lives (1.4 parked it after five reopens).

Also part of the bump, 2026-11-09 (pi 1.4.0 to 1.5.1):

- The conversation view is a window over the whole history on 1.5, newest 50 entries first and dropping its oldest 50 past 100. The thread stream asks for a window that starts with the newest 75 entries (what the thread window can hold) and never drops any, so appends stay appends for a subscription's life (`STREAM_WINDOW` in `PiDurableHarness.ts`); `hasMoreHistory` reads the view's `before`. A compaction no longer cuts the view: its summary is appended where it was written, and the entries before it stay.
- A wake and a declined brief's tell read whether the parent was stopped and admit their input in one commit (`submit(tx, draft)`), so a stop lands either before the read or after the input.

Gate: `judges/approval-kill.ts`, on a judge brain with the production seam, brain, extension set and boot repairs over a faux model: six kills while the gated `bash` waits on its approval, then a seventh life accepts it as the user. Measured on 2026-11-09, with every tool call kept: the real case passes (6 of 6 kills with the approval pending, the command ran once, the record accepted by the user, one result that is not an error); the control (pi-durable's own limit) fails as it must, its call ended "Tool bash was interrupted 5 times in a row; it is not run again", its record cancelled and the command never run. The review fixes of 2026-11-09 narrowed the kept tool calls to the waits above (`CrashLimit.test.ts` runs the rule on a store crashed five times: the call that waits on nothing ends, the approval and the named wait run on, the approval still pending); the gate is rerun after that integration. The status moves to accepted when the user accepts it.
