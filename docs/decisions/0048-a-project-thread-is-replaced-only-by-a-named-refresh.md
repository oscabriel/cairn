# A project thread is replaced only by a named refresh

Amends ADR 0026's amendment (one project thread per project). That amendment said a later launch in a folder project refreshes its project thread, and `ThreadLaunchInput.replaces` was optional: absent, a launch replaced whichever thread was current. The header's Refresh asked first and named the thread, but the draft hero did not: a plain Send on the landing page (the PWA's start page, defaulting to the most recently updated project, often the one whose thread was working) stopped the project thread's run, queue and working subagents and archived it, with no warning. `mod+n` and `mod+shift+o` (`chat.new`) reached the same hero. Nothing in the client listed archived threads, so the refresh confirm's "you can still open it from the archive" was untrue and the old thread could not be reached again (review findings V-1, V-2, U-1, U-2).

## Decisions

1. **The brain refuses an unnamed replacement.** A `thread.launch` of a new top-level thread into a folder project that has a live project thread is refused (`InvalidInput` on `replaces`, saying the project already has a project thread and how to replace it) unless `replaces` names that thread. The refusal is decided in the shell commit's planner (`planProjectThread`), and the launch stops the old thread only when `replaces` names it, so a refused launch stops nothing. A first launch in a project with no project thread still marks it; scratch launches, subagents and workflow nodes are not top-level folder launches and are unaffected.
2. **The client never launches over a project thread.** When the draft's project has a project thread, the hero's Send opens that thread with the draft's words and attachments moved into its composer, unsent, and a notice saying why; `chat.new` opens the project thread of the project the user is in. The only way to replace a project thread stays the header's Refresh, behind its confirm.
3. **Earlier project threads are reachable, read only.** `shell.previousThreads` pages a project's archived top-level threads, newest archive first, from the thread rows; archived rows stay out of the shell stream and its snapshot. The sidebar folds them under "Previous (n)" below the project thread; a row opens the thread's transcript with no composer, its subagent rows and work panel reachable (its children stay live rows under it), and a bar leading to the current project thread. A page reached any other way (Back, a reload, a link) is read only too: the client reads the thread from the fold's rows, or asks `shell.earlierThread`, which answers an earlier project thread by its id and `NotFound` for any other thread, when the live shell and the fold do not hold it. The refresh confirm now says the old thread can be opened under Previous.
4. **No unarchive of a project thread from the client.** Unarchiving an earlier project thread while another is marked is refused by the planner (ADR 0026), and offering it would only ever show that refusal or, with no live project thread, quietly bring an old conversation back as the project thread. Reading one is enough for now; making an earlier thread current again would be a refresh-like action with its own confirm, decided separately.

Judges and tests that launched a second top-level thread into one folder project now name the thread they replace (`ProjectThreadLaunch.test.ts`, `ThreadLaunch.test.ts`, `ProjectThread.test.ts`, `judges/push.ts`); `judges/behaviour.ts`'s hero sends start without a project once every seeded project has a project thread. `judges/tools.ts` launched into the user's own project on the deployed brain, where each of its launches archived that project's thread unasked; it now launches its three turns as scratch threads and clears them afterwards, so it never touches a project thread.

Decided by the user on 2026-11-09, adopting the product review's recommendations (V-1, V-2, U-1, U-2).
