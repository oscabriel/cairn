# A feature registers through one manifest, and the deployed brain composes no test double

The review of 2026-11-09 found that a folder was not a module: every top-level folder of `apps/server/src` but `db` sat in one import cycle of 22 folders, `brain/` imported 16 of them back, including the features built on it, and a feature had no place to register (finding Q-1). What a feature added went into a dozen lists in other folders: the extension set and its order key, the thread stream's documents, the boot repairs, the close hooks, the reactors, the crash limit's kept waits, the RPC handlers and the app's layers. The same review found the deployed entry loading about 6,000 lines of test doubles (Q-8), shared stores guarded by a comment asking for "the same reference" (Q-10), a stub table answering a forgotten RPC handler with "not available on this brain yet" (Q-9), and the approval ledger living in a file named for documents (Q-4).

## Decisions

1. **A feature registers through one manifest.** A feature's folder exports one `<Folder>Feature.ts` (`CairnFeature`, `brain/Feature.ts`) listing everything it registers: its extension sources and the services it builds for them, the `cairn.*` documents the thread stream carries for it, what an answer does in its commit for the records it owns, its part of a submit and of a Stop all, its boot repairs (each placed by a `RepairOrder` key), its close hooks, its reactors, the waits the crash limit keeps, its RPC handlers, the services it runs over pi-durable, and what the app runs for it. Twelve features have one: attachments, executor, approvals, subagents, workflows, verdicts, usage, models, reach, pi-host, skills and push. A manifest is declared with `satisfies CairnFeature`, so its precise type survives and the consumers' requirements are computed from it.
2. **One ordered list, folded whole by every consumer.** `apps/server/src/Features.ts` lists the manifests. The extension set (`ExtensionSet.ts`), the reactor host (`ReactorSet.ts`), the boot repairs (`BootRepairs.ts`), the close hooks (`ShutdownHooks.ts`), the RPC group (`rpc/Handlers.ts`'s `handlersOf`, applied in `AppLayer.ts`) and the app (`AppLayer.ts`'s harness and app layers) each fold the whole list. `Features.test.ts` passes the list through every fold with each manifest watched, and fails on a field no consumer reads, so a field cannot be added and forgotten.
3. **Order is stated where it matters.** An extension installs at its `ExtensionOrder` key and a boot repair runs at its `RepairOrder` key (`BootRepair.ts`); `BootRepairs.ts` states the rule the keys keep (a repair that needs a quiet Harness comes before `resume interrupted launches`). The list's order decides only the thread stream's document order (the thread's own `cairn.approvals` and `cairn.permissions` first, which the harness always carries, then subagents, workflows and verdicts) and the close order (the bridge, then the portal sweep, the reactors last). An answer's hooks act on their own records only, so their order is free. `Features.test.ts` holds all of it: the repair names in order with every key used once, the close names, the installed extension names.
4. **`brain/` imports no feature folder, but the approval ledger.** The brain defines the manifest's shape and reads only what a consumer hands it: the extension set gives the harness the features' documents and hooks (`Extensions.fromFeatures`), and the composition files at the root fold the list. The feature-specific files that sat in `brain/` moved to their features (the budget gate and `BudgetSources` to `usage/`, the health feed and the bridge's working folder to `models/`, the child workspace repair to `subagents/`, the entry image route to `http/`), and the brain reads git's version through `GitVersion` instead of the git runner. `ImportGraph.test.ts` refuses any other edge from `brain/` to a feature folder.
5. **What stays a deliberate direct dependency.** `brain/` imports `approvals/`: the seam answers a record and cancels the records a stopped run held (ADR 0024), the permission gate records an approval (ADR 0031), and the crash limit keeps a record's wait; the ledger imports `brain/` and nothing else, so the two are one small cycle, listed in the test. A document the brain's core or the ledger reads is declared in `brain/` beside the thread's own (`brain/CairnDocs.ts`): the subagents' documents (`brain/SubagentDocs.ts`) and the dispatch ledger's (`brain/WorkflowsDoc.ts`); the feature lists it in its manifest. The composition root keeps providing the services the app and the handlers read (the budget book, the push outbox, the reach services, the subagents' service over the app's child workspaces), each the one reference its module exports. The scripted harness, a test double, imports what it imitates. One cycle of thirteen folders remains among the app's own folders and the features they reach (`http/Routes.ts` lists feature routes that import `http/`'s helpers; the shell store reads the settings in `models/`; a thread's launch, turn stages and title model reach attachments, skills and spend; projects and git read each other); `brain/` is not in it. It is listed in `ImportGraph.test.ts` with that reason; routes as a manifest field and the shell's settings read are the next steps that would shrink it.
6. **The approval ledger is `approvals/`'s.** `brain/CairnDocs.ts` declares the thread's documents and nothing else; the ledger, its answer path and its two boot repairs are `approvals/ApprovalLedger.ts` (Q-4). What an answer does for a feature's records (a brief's Go, a launch's Go, accepted criteria) is a hook in that feature's manifest. The subagents' question route and decision options moved to `subagents/`, with the relay they belong to. `approvals/` imports `brain/` and nothing else.
7. **The deployed brain loads no test double.** A fake lives in a file named for what it is (`FakeExecutor.ts` with `FakeExecutorLink`, `FauxModels.ts` with `FauxModels.layer` and `FAUX_MODEL`, `ScriptedGoalBook.ts`, `ScriptedHarness.ts`), and the scripted brain is `DevLayer.ts`'s. `main.test.ts` walks `main.ts`'s value imports and refuses any file named like a fake, a faux model, a fixture, a kit, a stub or mock, the scripted harness, a dev layer or demo, or the conformance suite, with the dev and judge entry points as its control (Q-8).
8. **The deployed composition is one layer, built in a test.** `MainLayer.ts` is `main.ts`'s composition short of its edges. `Composition.test.ts` builds it with fakes at the edges through a memo map that records every context a constructor built, and holds each stateful service to one instance; a second constructor of one (a factory called twice, a second `Database.layer`) fails it. The memo map keeps one instance per constructor reference, so a second spelling over the same constructor is the same instance and not the hazard. A shared instance is exported once, by its owner: `DatabaseLive` (`db/DatabaseLive.ts`), `ModelHealthLive`, `SettingsLive`, `ReachLive`, `ChildWorkspaces.layer` (Q-10).
9. **The RPC group is complete by type.** The group is built from the real handlers only and typed as serving every RPC of `CairnRpcs`, so a handler in no manifest is a compile error naming its tag. The stub table is `rpc/StubHandlersTestKit.ts`, for tests that serve one domain over a complete group (Q-9).
10. **A sign-in store that cannot lock degrades.** The OAuth store whose lock cannot be taken at boot is built unavailable, logs `oauth_lock_failed`, and refuses every write with `unavailable`, as the Executor grant leaves Executor `disabled`: neither stops the brain from booting.
11. **Shelved features stay composed.** Host reach stays in the production composition behind its fence: its tools install only when porch is set up at boot (ADR 0038 as amended), and its boot repairs and close hook run as before. Codex sign-in (ADR 0037, still proposed) stays as it is, behind the OAuth store above.

## Adding under the new shape

- **A host tool.** In an existing extension: the tool, one file. As a new extension of an existing feature: the extension, its `ExtensionOrder` key in `brain/Extensions.ts`, and the feature's manifest (`extensionSources` and `extensionLayer`): three files, against three before plus the hand-written requirements union in `ExtensionSet.ts`; nothing in the extension set or `brain/` changes. A world-changing tool still opts into `gatedTool` by hand.
- **A card backed by a new document.** The protocol's schema and kind with `VISIBLE_DOCUMENTS`, `DOCUMENT_SCHEMAS` and the golden (two or three files in `packages/protocol/`), the token in the feature's folder (its state derived from the schema, ADR 0052), the token in the manifest's `documents`, then the client's logic and view: six to eight files, and no edit in `brain/` (the stream's list in `PiDurableHarness.ts` is gone). `StreamDocuments.test.ts` and `Features.test.ts` tie the manifests to `VISIBLE_DOCUMENTS` both ways. The scripted harness shows it only if the dev brain should.
- **A prelude verb.** Its six files (the review's count, with the two name lists `NODE_TOOLS` in `Prelude.ts` and `PRELUDE_NAMES` in `WorkflowScript.ts`) are all in `workflows/`, and the manifest does not change, since the verb's tool is in the workflows extension. This package does not merge the two lists.
- **A feature (phase 3's stones).** Its folder with its manifest, and one entry in `Features.ts`; an `ExtensionOrder` key for each extension and a `RepairOrder` key for each repair.
