# What the deployed brain composes

The review of 2026-11-09 found the deployed entry (`main.ts`) loading about 6,000 lines of test doubles, because production modules carried their fakes as statics (`ExecutorLink.layerFake`, `GoalBook.layerScripted`, `ModelSource.layerFaux`) or sat beside them (`ScriptedBrain` in `AppLayer.ts`); its shared stores guarded by a comment asking each entry point for "the same reference"; and its RPC group completed by a stub table that answered a forgotten handler with "not available on this brain yet" (findings Q-8, Q-9, Q-10).

## Decisions

1. **The deployed brain loads no test double.** A fake lives in a file named for what it is (`FakeExecutor.ts` with `FakeExecutorLink`, `FauxModels.ts` with `FauxModels.layer` and `FAUX_MODEL`, `ScriptedGoalBook.ts`, `ScriptedHarness.ts`), and the scripted brain is `DevLayer.ts`'s. No module `main.ts` reaches imports one; `main.test.ts` walks `main.ts`'s value imports and refuses any file named like a fake, a faux model, a fixture, a kit, a stub or mock, the scripted harness, a dev layer or demo, or the conformance suite, with the dev and judge entry points as its control.
2. **The deployed composition is one layer, built in a test.** `MainLayer.ts` is `main.ts`'s composition short of its edges (the porch and units, the pi tools, the bridge, Executor, the OAuth store, the keys, the identity rules, the settings, the platform). `Composition.test.ts` builds it with fakes at those edges through a memo map that records every context a constructor built, and holds each stateful service (the database, the health and settings stores, the budget book, the push outbox, the reach services, the brain, the seam, the extension set and more) to one instance. A second constructor of a stateful service (a factory called twice, a second `Database.layer`) fails it; the memo map keeps one instance per constructor reference, so a second spelling over the same constructor is the same instance and is not the hazard.
3. **A shared instance is exported once, by its owner.** `DatabaseLive` from `db/DatabaseLive.ts`, `ModelHealthLive` from `models/ModelHealth.ts`, `SettingsLive` from `models/SettingsStore.ts`, `ReachLive` from `reach/ReachLayer.ts`, `ChildWorkspaces.layer`; `AppLayer.ts` exports none of them.
4. **The RPC group is complete by type.** `rpc/Handlers.ts` builds the group from the real handlers only and types it as serving every RPC of `CairnRpcs`, so a handler that is written but not listed is a compile error naming its tag. The stub table is `rpc/StubHandlersTestKit.ts`, for tests that serve one domain over a complete group.
5. **A sign-in store that cannot lock degrades.** The OAuth store whose lock cannot be taken at boot (no `flock`, a state or data directory it cannot write) is built unavailable, with an `oauth_lock_failed` error line, and refuses every write with `unavailable`, as the Executor grant leaves Executor `disabled`: neither stops the brain from booting.
6. **The approval ledger is `approvals/`'s, and the documents the brain reads are `brain/`'s.** `brain/CairnDocs.ts` declares the thread's documents (the receipt, the metadata, `cairn.approvals`, `cairn.permissions`, the entry kinds) and nothing else; the ledger, its answer path and its two boot repairs are `approvals/ApprovalLedger.ts` (finding Q-4). A document the brain's core or the ledger reads is declared in `brain/` beside them: the subagents' documents (`brain/SubagentDocs.ts`: a Stop all reads the registry, the gate walks `cairn.child`, a child's question settles with its parent's mirror) and the dispatch ledger's document with the two rules the approval ledger applies to it (`brain/WorkflowsDoc.ts`: a cancelled launch declines its row; a node's brief is held by its run). What an answer does in its commit for a feature's own records (a brief's Go, a launch's Go, accepted criteria) is a hook the feature gives the extension set, never an import of the harness. The subagents' question route and its decision options moved to `subagents/` with the relay they belong to. So `approvals/` imports `brain/` and nothing else.
7. **Shelved features stay composed.** Host reach stays in the production composition behind its fence: its tools install only when porch is set up at boot (ADR 0038 as amended), and its boot repairs and close hook run as before. Codex sign-in (ADR 0037, still proposed) stays as it is, behind the OAuth store above. Both are in `main.ts`'s closure on purpose; phase 3's portal work edits them in place.

Decided on 2026-11-10 in the review fix program (package E1-modules), under the user's instruction to go with the reviewer's recommendations (findings Q-8, Q-9, Q-10); the shelved features' place in the composition was decided in the package instructions.
