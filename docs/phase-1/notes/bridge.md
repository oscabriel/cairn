# Phase 1 notes: the Claude bridge

Written 2026-10-22 on the Beelink against pi 1.4.0 (pi-ai, pi-durable), Effect 4.0.5, Node 26.11, Agent SDK 0.3.305 (bundled `claude` 2.1.305), t3code `fe27e8e3`. No file under `apps/`, `packages/` or `spikes/` was changed. Experiments ran in `/tmp/bridge-direct` (scripts named below; they are not kept, and the load-bearing option set is quoted in section 2.6). Sibling notes in this folder: `brain.md`, `edges.md`, `server.md`, `client.md`, `v1.md`. Where this note disagrees with one of them, section 4 says so.

## 1. Summary

1. **Port, do not register.** pi-claude-bridge 0.9.3 does load unmodified on pi-ai 1.4.0 through v1 spike 1's stand-in extension API (re-run today, section 2.2). But direct registration cannot deliver seven of the twelve Phase 1 requirements (section 3.1): it sets a process-wide env var that breaks the usage probe, keeps its state in module singletons, strips no `ANTHROPIC_*`, leaves `settingSources` at the default, has no semaphore, no stored session id, no explicit abort for a held query, and no `alwaysLoad`. Run the direct attempt once, timeboxed, as step 0 so the ADR cites numbers; then port.
2. **The three fixes stay, but the second one gets much cheaper.** One abort signal per conversation and the stored session id carry over from v1 unchanged. Native resume no longer needs to edit Claude Code's JSONL transcript: the Agent SDK's own `resume` + `resumeSessionAt` (+ `forkSession`) did it in today's experiments with no `cc-session-io` (cache read to write 11,021/140, 11,030/130 and 11,161/0, against 0.07x for a rebuild). That removes about 1,400 lines of v1 (`native-resume.ts`, `native-fork.ts`, most of `rebuild.ts`) from the first slice. A history-import rebuild (cc-session-io) stays as the second-slice fallback.
3. **Store the session id as a stamp on the assistant message** (`AssistantMessage.diagnostics`, exists in pi-ai 1.4.0), not in a side document. It commits in the same transaction as the assistant entry, so there is no crash window, and it rides along into forks. This also answers `brain.md` open question 8 (forks on the bridge) for free.
4. **Concurrency:** a semaphore of 4 that counts children generating, not children held open across a tool call. A held child costs about 232 MB and no API traffic; counting it would deadlock a parent waiting on its subagent. Add a separate cap on live children and an idle time to live, enforced with Effect's `RcMap`.
5. **Usage windows:** probe (SDK `usage_EXPERIMENTAL_...`, 442 ms, $0) plus every `rate_limit_event`, merged by window id into one `SubscriptionRef`. Port the mapping from t3code `fe27e8e3` `apps/server/src/provider/claudeUsageLimits.ts` (238 lines), not v1's copy of `c079503`: the pinned one adds a monthly spend window. Do not refuse turns on a threshold in the bridge.
6. **Retry trap in pi-durable 1.4.0:** `rate.?limit` and `429` are in pi-ai's retryable error pattern, `quota exceeded` is in the non-retryable one and wins. A spent plan window must be reported as "Claude plan quota exceeded ..." or pi-durable will retry it three times with backoff.
7. **Refusing pi-ai's Anthropic OAuth** takes four layers, all fail-closed (section 3.7): a credential store that hides `anthropic`, an `AuthContext` that hides three env names, a replacement `anthropic` provider without `oauth` auth, and a conformance test with a fetch spy. The user's `auth.json` `anthropic` entry has the prefix `sk-ant-usr`, which is neither `sk-ant-api` nor `sk-ant-oat`; ADR 0002's statement that it is a metered key is unverified. Fail closed and ask the user.
8. **Pin the Agent SDK at 0.3.305** for now (the version Phase 0 measured). Latest on npm today is 0.3.308 (bundles 2.1.308); 0.3.306 to 0.3.308 are version-parity releases. Bump only with a rerun of the bridge judges, and re-read Anthropic's legal page at every bump.
9. **Names:** the glossary already uses "Parked" for a pi-durable task. The bridge's "parked query" must be called a **held query**. `judges/bridge-orphans.sh` is the stdio relay's judge and breaks the glossary's own rule about the word "bridge"; name the Claude judges `judges/claude-*`.
10. **Evidence gaps to close in Phase 1:** a real turn through the whole path on pi-durable 1.4.0 (Phase 0 measured only the SDK child), a 20-minute held tool call, and the Opus and Sonnet versions of today's Haiku resume experiments.

### 2.2 pi-claude-bridge: mechanism, and what it cannot do for Cairn

Mechanism (`src/index.ts` at `874fa7c`): `streamClaudeAgentSdk` (L1766 to 2214) starts an Agent SDK `query()` with `tools: []`, `permissionMode: "bypassPermissions"`, `includePartialMessages: true`, `systemPrompt: {type:"preset", preset:"claude_code", append}`, `settings.includeGitInstructions: false`, `claudeMdExcludes`, `--strict-mcp-config` and `effort` from the reasoning level. pi's tools are served to Claude Code by `createToolServer` (`src/mcp-server.ts`, 169 lines) as one in-process MCP server named `custom-tools` (tool names `mcp__custom-tools__<name>`). A tool handler blocks on a promise until pi returns the tool result through the next `streamSimple` call (`buildMcpServers` L1069, `deliverToolResults` L1644). Pairing is by `_meta["claudecode/toolUseId"]`. The prompt is a long-lived async generator (`src/prompt-stream.ts`) so a steer can be written to the child's stdin before the tool result.

Registration: the extension default export (L2416 to 2733) calls `pi.registerProvider("claude-bridge", {baseUrl, apiKey: "not-used", api: "claude-bridge", models, streamSimple})` and `pi.on(...)` for nine events (`session_start`, `session_before_compact`, `session_before_tree`, `before_agent_start`, `agent_start`, `turn_start`, `session_shutdown`, `session_compact`, `session_tree`), plus `registerTool` for AskClaude.

**Re-run today (E6, `/tmp/bridge-direct/probe.ts`)**: with pi-ai, pi-coding-agent and pi-tui 1.4.0 installed beside `src/` from `874fa7c`, the stand-in API of v1's `spikes/01-bridge/bridge.ts` still works. The extension touched exactly the nine `on` events and `registerProvider`, registered 14 models, and set `process.env.CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC = "1"` for the whole process (it was unset before). With the default `plan: "pro"` it registers `claude-opus-4-6` at 200K. The install is 510 MB of `node_modules`.

What direct registration cannot give Cairn (each is read from the source, not guessed):

| Requirement | Upstream state |
| --- | --- |
| One abort signal per conversation | The first call's `options.signal` gets `onAbort` (L2093 to 2094 on `main`). Upstream `main` (commits `38980d1`, `1ae18a2`, "UNRELEASED") binds each later run's signal and ignores its abort once that run's stream ended, which fixes the later runs only. pi-durable aborts the first generation's signal with `Error("Task N invocation has ended")` when that generation parks on its tool round (`harness/scheduler.js` L1920), so the held query still dies at the first tool call |
| Resume Claude Code's transcript | `sharedSessions` is an in-memory map keyed by pi session id (L244). After a restart it imports pi's history into a new session with `cc-session-io` (`syncSharedSession` L724 to 853). v1 measured 1,617 read / 22,256 write (0.07x) for that path |
| Store `session_id` in pi-durable | Not stored anywhere |
| Semaphore | None. Any number of children |
| `settingSources: []`, `disableAllHooks` | Provider path leaves `settingSources` at the SDK default, so `~/.claude` hooks fire inside thread turns (v1 spike 1 "Noticed") |
| Strip `ANTHROPIC_*` | Spreads `process.env` into the child (L2031); `CC_CHILD_ENV` (L48) only adds two variables |
| Keep process env clean | Sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` globally at activation (L2418), which makes the usage probe return null windows |
| Per-conversation isolation | `ctx()` is a module-global `QueryContext`; a second concurrent query is treated as a "reentrant subagent" (L1879) and routed by tool call id. v1 brief section 4 calls this the largest port risk |

| Deprecated import | `getModels` from `@earendil-works/pi-ai/compat`, whose header says it is deleted with the coding-agent ModelManager migration |

What upstream does well and Cairn should keep: the tool-result delivery state machine with the two maps, `flattenRootCombinators` in `mcp-server.ts` (Claude Code drops a tool whose schema has a top-level `anyOf`, `oneOf` or `allOf`, and the call then runs twice or hangs), the resumed-tool-result path (0.9.3 fix #174: a result with no held query resumes the session with a continuation prompt), `thinking` signature handling, "tool calls dispatch only when their block closes" (#146), and the 0.9.3 change that an exhausted plan window leads with "Claude quota exceeded" (#183), which is what makes pi not retry it.

### 2.3 How pi-durable 1.4.0 calls a provider

- The generation task's `request` phase calls `runtime.models.streamSimple(model, {messages}, options)` with `options = {...settings.stream, signal: runtime.signal, telemetry, sessionId, reasoning?}` (`dist/harness/generation.js` L120 to 133, 353). `sessionId` comes from `ensureProviderSessionId`: the `pi.provider` conversation document, created lazily, persisted, unique per conversation, fresh per fork (`dist/harness/provider.d.ts`). `reasoning` is omitted when the thinking level is `off`. No cwd, no conversation id, no `onResponse`.
- `settings.stream` is a host setting read at each resolution and not per conversation (spec L447 to 452: "Read at every resolution and never copied"). v1 put the cwd in `settings.stream.metadata.cairnCwd`, which works only with one Harness per thread.
- Compaction calls `runtime.models.completeSimple(model, {messages}, {cacheRetention: "none", sessionId, ...})` (`harness/compaction.js` L122 to 129). Upstream already routes `cacheRetention === "none"` to an isolated `persistSession: false` child; keep that.
- `Models.streamSimple` resolves `Provider.auth` first and then dispatches to `Provider.streamSimple(model, TranscriptContext, options)`. `TranscriptContext` carries the system prompt and tool declarations as leading `role: "system"` messages. pi-ai 1.4.0 exports `getCurrentSystemMessage`, `getCurrentSystemPrompt`, `getCurrentTools`, `getSystemMessageText`, `withoutInitialSystemMessage` (`dist/utils/transcript.d.ts`, `dist/utils/text.d.ts`). They replace upstream's `transcript.ts` `SECTION_RANK` logic: sections render in pi-durable's replay order.
- `AssistantMessage.diagnostics?: {type, timestamp, error?, details?: JsonObject}[]` and `StopReason` now includes `"pending"` and `"deferred"` (`dist/types.d.ts` L307, L368 to 380). The generation task stores the message as given (`appendAssistant`), so a diagnostic written by the provider commits with the assistant entry. v1 proved this on 1.3.0; re-prove on 1.4.0 (judge J4).
- Abort sources (`dist/harness/scheduler.js`): invocation end `controller.abort(endedError(invocation))` (L1920, `Error("Task N invocation has ended")`); abort request `controller.abort()` (L473, default `DOMException` `AbortError`); `join()` on close `controller.abort()` (L331, same `AbortError`). Only the last two are real; the first is routine and happens at every tool boundary. A user abort of a tool call while the query is held reaches the bridge through no live signal, because the generation invocation already ended, so Cairn must call `abortConversation(sessionId)` itself.
- Hooks (spec section 7.2, `dist/index.d.ts` exports `hook`, `GenerationTask`, `AgentDoc`, `ProviderDoc`, `defineExtension`): `beforeRequest(request, api, context)` runs before every request attempt including recovery, off the Session line, and `HookApi` can `snapshot(AgentDoc | ProviderDoc, api.conversationId, context)`. Hooks are read-only; they cannot commit documents. `HarnessOptions.conversationCreated(tx, conversation)` runs in the commit that creates or forks a conversation.
- 1.4.0 specifics that touch the bridge: `HarnessOptions.models` and `.settings` accept functions (`harness/types.d.ts` L554, L564); a task cut off by a crash five times in a row is parked (`settings.restartLimit`); generation retry backoffs now sleep durably; `HarnessOptions.identity` sets `User-Agent` and attribution for HTTP providers and does not reach the bridge.
- pi-ai's retry classifier (`dist/utils/retry.js` L4 to 70): `isRetryableAssistantError` first tests the non-retryable pattern (`quota exceeded`, `billing`, `out of budget`, `available balance`, ...), then the retryable one, which includes `rate.?limit`, `too many requests`, `429|500|502|503|504|520|524`, `overloaded`, `timed? out`, `timeout`, `terminated`, `stream was interrupted`, `fetch failed`. Defaults: 3 retries, 2 s base delay, 60 s cap.

### 2.8 Anthropic OAuth inside pi-ai 1.4.0

- `anthropicProvider()` (`dist/providers/anthropic.js`) offers two auth methods: `apiKey` (stored key, else env `ANTHROPIC_AUTH_TOKEN` as a Bearer header, else `ANTHROPIC_OAUTH_TOKEN`, else `ANTHROPIC_API_KEY`, else workload identity federation) and `oauth` (`lazyOAuth({name: "Anthropic (Claude Pro/Max)", isSubscription: true})`).
- The spoofing is in `dist/api/anthropic-messages.js`: `isOAuthToken(apiKey)` is `apiKey.includes("sk-ant-oat")` (L780 to 781); such a key gets `user-agent: claude-cli/<ver>`, `x-app: cli`, beta features `claude-code-20250219` and `oauth-2025-04-20` (L800 to 815, L871 to 872), and tool names rewritten with `toClaudeCodeName` (L545, L1075, L1172, L1320). This is mechanism (2) of research 05 section 2.6 and is prohibited.
- Note the asymmetry: an OAuth token reaches that path from three directions: a stored `oauth` credential, a stored `api_key` credential whose value is an `sk-ant-oat` token, and any of three env vars.
- `~/.pi/agent/auth.json` has three entries (checked by type and key prefix class only; no value is recorded here): `opencode-go` (`api_key`), `anthropic` (`api_key`, 106 characters, prefix `sk-ant-usr`), `openai-codex` (`oauth`). The Phase 0 check the kickoff asked for ("`sk-ant-api` or `sk-ant-oat`") has an answer that is neither. pi-ai would send this key as an ordinary `x-api-key` without the spoof headers, but nothing in the repo shows it is a metered Console key.
- `createModels(options?: {credentials, modelsStore, authContext, identity})`, `builtinProviders()`, `builtinModels(options)` and `MutableModels.setProvider / deleteProvider` are the composition points (`dist/models.d.ts`, `dist/providers/all.d.ts`). `ModelRuntime` (pi-coding-agent, `src/core/model-runtime.ts`) wraps them and accepts a `credentials: CredentialStore` option and `registerNativeProvider`.

## 3. What Cairn should build

### 3.1 Register or port

Recommendation: **port as a native pi-ai provider with source headers, after one timeboxed direct attempt.**

Step 0 (two hours, `spikes/6-bridge-direct/`, with a `NOTES.md`): copy v1's `spikes/01-bridge/bridge.ts` stand-in, load upstream `main` (`1ae18a2`) on pi-durable 1.4.0, run one real Haiku turn with a tool, one `kill -9` while the tool call is held, and the probe. Record: cache read to write after the restart (expect about 0.07x), the process env side effect, the number of `claude` children for two concurrent threads, and which hooks in `~/.claude/settings.json` fired. Write ADR 0016 "The bridge is ported, not registered" citing those numbers (the kickoff asks to try direct first; v1 did it on 1.3.0 and Phase 0 did not repeat it, so the cheap re-run is the honest way to close that line). The expected outcome is the table in 2.2.

If the user would rather keep the port minimal, the middle path is a wrapper around upstream `src/` that injects `__test.setQuery` to rewrite SDK options (strip env, `settingSources: []`, semaphore). It still keeps module singletons, `pi-coding-agent` and `pi-tui` at import time, the notice and config machinery, and a private test hook as its extension point. Not recommended.

### 3.2 Module layout and boundaries

Standards S42 and S43 apply: the Agent SDK sits behind exactly one Effect service, pi-durable calls into Cairn through a `ManagedRuntime`, pure helpers stay plain TypeScript, and ported code is re-cut (no `any`, no `!`, no `as` without the SAFETY protocol; `spikes/**` is exempt from lint but ports are not). I recommend a package, `packages/claude` (`@cairn/claude`), because judges and the scripted harness need to build the provider without the server's composition root (S6: a second consumer). `apps/server` provides the layer.

### 3.3 The three fixes, in 1.4.0 terms

**1. One abort signal per conversation.** The conversation, not the generation, owns the query's lifetime. Bind each call's signal with `abortKind(signal.reason, closing)` (v1 `claude/abort.ts`, 25 lines, own code): `reason instanceof DOMException && reason.name === "AbortError"` is real, anything else (the `Error("Task N invocation has ended")`) is ignored. Three more rules, all from v1 D8 and still correct against `scheduler.js`: (a) the brain's abort path (`Harness.abort` for a conversation) must also call `Claude.abortConversation(sessionId)`, because a held query outlives its generation task and no signal reaches it; (b) shutdown calls `beginClosing()` before `harness.close()`, because `join()` aborts invocations with the same `AbortError` as a user abort; a closing kill leaves the session resumable; (c) on a real abort, release pending tool handlers by resolving them (a rejected MCP handler wedges the call), fail the prompt stream, then `interrupt()` and `close()` (both are needed). `edges.md` item 8 plans `KillMode=mixed` with SIGTERM first, which matches (b).

**2. Resume Claude Code's transcript natively.** The decision table in `ClaudeResume.ts`, evaluated on every provider call that has no held query able to take it:

| State | Action | Evidence |
| --- | --- | --- |
| Held query owns the incoming tool results (by tool call id) | Deliver them to the waiting handlers; steer first if pi appended a user message | upstream `deliverToolResults`, v1 `conversation.ts` |
| No held query; last stamp matches the history; tail is tool results, or a user prompt | `query({resume: stamp.ccSessionId, resumeSessionAt: stamp.ccUuid})`; tool results that Claude Code does not hold go in the continuation prompt text; a user prompt goes as the prompt | E1, E2 |
| Same, but the previous child may still be writing (real abort, child error, unknown state) | Add `forkSession: true` so the new query writes to a new file | E3 |
| No held query, no usable stamp in this conversation, but the history holds stamps (a fork of a pi conversation, or a stamp from before an edit) | `forkSession(stamp.ccSessionId, {upToMessageId: stamp.ccUuid})` then resume the fork | E3, v1 fork check |
| Stamp present but history diverged (edit, compaction, other-provider turns), transcript missing (30-day sweep, cwd moved), or the SDK refuses the cut | Rebuild from pi's history with `cc-session-io` (second slice), cold | v1 `rebuild.ts` |

What the stamp must carry (one more field than v1): `ccSessionId`, `ccUuid` (the SDK `uuid` of the last chain entry of the reply: the last `assistant` message, or the one holding the `tool_use`), `historyDigest`, the instruction state the session holds (section digests, 3.4), `cliModel` (with `[1m]`), `cwd`. v1's `ccMessageId` (the API message id) only helped its JSONL cut and can go. For the cut after a tool result, read the uuid of Claude Code's own `tool_result` entry with `getSessionMessages` at resume time (E2), so nothing extra needs capturing during the turn.

Do not copy v1's `native-fork.ts` (944 lines), `history-digest.ts` plus `convert.ts` import logic for the common paths, `native-images.ts` or `session-verify.ts` into the first slice. Port `history-digest.ts` (171, dot314) because the stamp check needs a digest of pi's history.

Open point: the experiments delivered a tool result for a dangling call as prompt text. A coherent alternative, which keeps Claude Code's view faithful, appends a real `tool_result` record to the transcript with `cc-session-io` (v1 `native-resume.ts`, 141 lines). Only build it if J3 shows Sonnet or Opus rerunning tools.

**3. Store the session id in pi-durable.** Use the stamp on the final `AssistantMessage` of each reply: `diagnostics: [{type: "cairn.claude", timestamp, details: {...}}]` (v1 `session-map.ts`, rewrite). Reasons it beats `brain.md` open question 4's `cairn.claude-session` family document: a provider cannot commit from inside `streamSimple` without racing the generation task's own commit (spec section 12, "Long transactions"; hooks are read-only), the stamp is atomic with the assistant entry, it needs no new document schema or migration, and it follows entries into forks, so `conversation.fork` at entry E gives the fork a native Claude fork with no extra code. Cost: it travels in `entries[].model` to clients; the server's `visibleView` should strip `cairn.claude` diagnostics before sending (they are small). A reply that compaction removed has no stamp; the bridge then rebuilds, which is correct.

The `sessionId` option of `query()` (a valid UUID) can be set to pi's provider session id for a conversation's first Claude Code session. pi-durable's id is a UUIDv7 and valid. That makes the first transcript findable even if the stamp was never committed (a kill during the very first reply). Later sessions (forks, rotations) get other ids, so the stamp stays the source of truth.

### 3.4 Running it: semaphore, usage, reminders, isolation

**Semaphore (cap 4).** Use `Semaphore.make(4)` (`effect/Semaphore` has `withPermit`, `take`, `resize`). Count permits for children that are generating, not for children that are held:

- Acquire when a turn starts streaming (the prompt is pushed, or a tool result is delivered and Claude Code resumes generating); release when that turn's stream ends in `done` or `error`, or the child dies.
- A held child holds no permit. Otherwise a parent waiting on a subagent (Phase 2) holds a slot its child needs, and the workflow deadlocks.
- A second, larger cap on live children (suggest 12, about 3 GB at 232 MB each) and an idle time to live (suggest 10 minutes) are enforced by an `RcMap` keyed by `sessionId`. Closing an idle child is safe because the next call resumes natively (E1 to E3); that is also why the Phase 0 measurement of 232 MB per held child is no longer a hard constraint.
- Expose the queue depth so the UI can say "waiting for a Claude slot". The provider must still return its stream at once and push `start` only after the permit arrives.
- `Semaphore.resize` lets the usage service shrink the cap to 2 when the weekly window passes 80 percent. Do not refuse turns by threshold in the bridge; v1's 95 percent refusal lived in `Children.ts`, and `research/09` lists it among the untested-orchestration failures. A real rejection arrives as Claude Code's own error.

**Stream idle watchdog.** A child can stall silently. dot314 `stream-idle-watchdog.ts` (152 lines) uses 90 s without any chunk, excludes time spent waiting on pi's tools, and honors a quiet period the child announces before an API retry. Re-cut it with `Stream.timeout`-style Effect code. pi-durable's `settings.stream.timeoutMs` is for HTTP transports and does not cover this.

**Usage windows.** Two sources, one `SubscriptionRef<ReadonlyArray<ProviderUsage>>`:

- The probe: a query whose prompt stream never yields, `settingSources: []`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` unset, `await q.initializationResult()` for the account and `q.usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({skipBehaviors: true})`, retried every 500 ms up to 10 times while `rate_limits_available && !rate_limits`; 10 s timeout; single flight. v1 `claude/probe.ts` (143 lines, own code) is the base. Cadence (v1 D5): boot, first watcher when the last probe is over 60 s old, every 5 minutes while a Claude turn runs or a client watches, once after a rejection, never on an idle timer.
- `rate_limit_event`s from every turn: utilization is a 0 to 1 fraction, resets are epoch seconds (the probe returns 0 to 100 and ISO strings). The event also carries `isUsingOverage` and `overageInUse`.
- Window ids, labels and the overage-included naming rule: port from t3code `fe27e8e3` `claudeUsageLimits.ts` (238 lines), rewritten in Cairn's types. The pinned version differs from v1's `c079503` copy: it adds `windowDurationMins` (300 and 10,080), a `monthly_spend` window computed from `rate_limits.spend` or `extra_usage`, and `scopedWindowId`. The `rate_limits` shape in `SDKControlGetUsageResponse` (0.3.305) types `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_oauth_apps` and more, but `model_scoped` and `spend` are read structurally; decode them with a Schema and degrade to "unknown" on a shape change, never to zero.
- Derive the plan from the probe's `subscription_type` and use `claude.plan` in config only as an override. v1 made `[1m]` model ids depend on a config value (`MEASURED_ONE_M` and `PLAN_GATED_ONE_M` in upstream `models.ts`); an unentitled `[1m]` id fails every turn.
- Report to the UI through the shell stream as `ProviderUsage` (client notes own the schema). t3code's mobile composer already shows these windows (`apps/mobile/src/features/threads/ComposerUsageLimits.tsx` at `fe27e8e3`).

**System-reminder delivery.** Claude Code stores the whole prompt, append included, as a `prompt_snapshot` at session start and reuses it on resume (v1 spike 4, confirmed by the stamp experiment: E3's prefix read 11,161 tokens after the append was ignored). So the append goes only to a new session. Every later change reaches the model as one `<system-reminder>` text block ahead of the next user message's content (not on tool-result continuations, which a held query cannot take). v1 `system-reminder.ts` (285 lines, own code) is the base: it digests the effective instruction state (leading system message plus replayed `sections` and tool declarations, never raw `pi.system` entries, because a compaction writes a complete baseline that restates unchanged values), keeps a per-section digest in the stamp so the reminder names exactly the sections that changed or were removed, and caps a diff. Use pi-ai 1.4.0's `getCurrentSystemMessage` for the replay. Do not use `renderSystemMessageUpdate`; its framing is documented as request-time only and may change between versions. `edges.md` item 7 and its judge assume this delivery (140 skills, about 30 KB); a large section re-sent in full on each small change is the accepted cost, and a line diff under 4 KB per section is the v1 mitigation.

**Keeping pi's preamble out.** pi-durable's prompt carries neither marker (grep of `pi-durable/dist`, `pi-ai/dist` and `pi-codemode/dist` finds neither `operating inside pi` nor the two doc paths; the text lives in pi-coding-agent's `core/system-prompt.js`). So skip upstream `prompt-capture.ts` (420 lines) entirely. Keep three things: (1) `assertSendablePrompt` on the append and on every reminder (v1 `prompt-safety.ts`, 33 lines): refuse `You are an expert coding assistant operating inside pi` at a line start, or both `docs/custom-provider.md` and `docs/packages.md`; extend the list with pi's documentation routing line, since upstream's August finding isolated lowercase `pi packages` there; (2) the third-party hint for Anthropic's own 400 ("Third-party apps now draw from your extra usage", dot314 `third-party-rejection.ts`, 35 lines), phrased without any retry or overflow trigger word; (3) a live eligibility canary (J7) that sends the real Cairn system prompt and fails if the rate-limit event shows `isUsingOverage: true`. Any Cairn extension that wants pi-coding-agent's own prompt text (skills formatting is fine, the preamble and docs lines are not) must go through the same guard.

**Isolation, `settingSources: []`, hooks, env.** One function builds every child's options (v1 `query-options.ts`, 83 lines, headers from upstream `index.ts` L48 to 64):

- `env`: the brain's env without `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, anything `ANTHROPIC_*` or `CAIRN_*`; plus `ENABLE_CLAUDEAI_MCP_SERVERS=0`, `DISABLE_AUTO_COMPACT=1`, `CLAUDE_CODE_FORK_SUBAGENT=0`; plus `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` for turn queries only, never in `process.env`, because the probe needs it unset. Stripping is not reading: Cairn never looks at the values.
- `tools: []` asserted at construction (`assertNoTools`; `bypassPermissions` is safe only because Claude Code has no tools of its own).
- `settingSources: []`, `settings: {disableAllHooks: true, autoMemoryEnabled: false, includeGitInstructions: false, claudeMdExcludes: ["**/CLAUDE.md", "**/AGENTS.md", "**/.claude/rules/**"], cleanupPeriodDays: <large>}`, `strictMcpConfig: true` (a typed option in 0.3.305 at `sdk.d.ts` L2348; upstream passed it as `extraArgs`), `persistSession` left true (resume needs the file), `includePartialMessages: true`.
- Assert the init message: `apiKeySource === "none"` (E5) and `tools.length === 0` and `mcp_servers` names only the bridge's server. A child that reports an API key source or extra tools is not a subscription child; fail the turn with a clear message.
- `cleanupPeriodDays`: the SDK sweeps local transcripts older than 30 days by default. A thread idle for a month then falls back to a cold rebuild, which works but costs. Setting a large value in the child's `settings` helps only for sweeps those children run; the user's interactive `claude` sweeps with its own settings. Recorded as an open question (section 4, Q8).

**`alwaysLoad` on the in-process MCP server.** Phase 0 measured that with `tools: []` a single bridged tool is not deferred, with or without `alwaysLoad`, and recommended setting it anyway. The mechanism matters for the port: `createSdkMcpServer({alwaysLoad: true})` sets `_meta["anthropic/alwaysLoad"]` on each tool (`sdk.d.ts` L647 to 652), and the typed `McpSdkServerConfig` (L1221) has no `alwaysLoad` field. Upstream's hand-rolled `createToolServer` returns `{type: "sdk", name, instance}` and builds its own `tools/list` answer, so the port must add `_meta: {"anthropic/alwaysLoad": true}` to each tool there. The SDK doc also says `true` blocks startup until the server connects (5 s cap), which is what is wanted since the tools must exist when turn 1's prompt is built. Judge J5 asserts the tool appears in `system:init` and is called with no `ToolSearch` round trip, with a deliberately large tool list.

**Tool timeout.** `McpSdkServerConfig.timeout` and `MCP_TOOL_TIMEOUT` set a hard wall-clock limit per tool call (`sdk.d.ts` L1225). The default was not verified here. A held call waits on pi-durable's tool (a 15-minute `bash`, a human approval, a subagent). Set `timeout` explicitly (suggest 4 hours) and run the 20-minute held-tool judge from `edges.md` (`bridge-approval-parked --slow`).

**Thinking off.** pi-durable omits `reasoning` when the level is `off`; upstream then passes no effort and no `thinking` option, so Claude Code's default (adaptive) applies. The SDK has `thinking: {type: "disabled"}` (`sdk.d.ts` L1939). Mapping `off` to it makes the control honest; changing it between turns of one session may cost cache. Test before shipping (J3 variant).

### 3.6 The cwd question

The provider call carries no cwd. `brain.md` open question 4 recommends a deterministic empty directory `<data>/claude-cwd/<sessionId>` for every child; v1 passed the thread's real cwd through `settings.stream.metadata.cairnCwd`, which is host-wide in 1.4.0 (works only with one Harness per thread). My recommendation: run Claude Code in the conversation's real arms cwd for host threads, and use the scratch directory only where the arms are elsewhere.

- Why the real cwd: Claude Code's preset puts a working-directory line into the prompt, and the model uses pi's `bash` and `read` with that directory. A scratch path in that line next to a project path in Cairn's own `cwd` section is two different answers to "where am I". The upstream fix #175 (0.9.3) exists because hosts that ran the child in the wrong directory misled the model and mirrored sessions under the wrong project.
- How, with a shared Harness: a Cairn extension with `hook(GenerationTask, {beforeRequest})` that reads `AgentDoc.cwd` and `ProviderDoc.sessionId` (both exported) and calls `Claude.noteConversation(sessionId, {cwd})` before every request attempt, recovery included. It covers subagents and forks, which a per-thread `metadata` setting cannot. With one Harness per thread (`server.md` question 1 recommends per-thread stores) either works.
- For a stone (ADR 0010) the arms path is a container path that does not exist on the Beelink. Use the scratch directory there, and say so in the thread's instructions section so the model is told which paths its tools use. Mark as risk R6.
- Realpath the cwd first: Claude Code keys transcripts by the symlink-resolved path (upstream `debugSessionPaths`, L708).
- A cwd change (worktree handoff) invalidates `resume`, because the transcript lives under the old cwd's project folder. `brain.md` already says change `cwd` only while idle; the bridge treats a cwd mismatch with the stamp as "rebuild".

### 3.7 Refusing pi-ai's built-in Anthropic OAuth

Defense in depth, all fail-closed, in `brain/Models.ts` (where `brain.md` L285 already puts the credential store) and tested by a bridge-owned judge:

1. **Credential layer.** `CairnCredentialStore` (read-only `auth.json` API keys plus Cairn's own OAuth store, ADR 0009) returns `undefined` from `read` and `list`, and refuses `modify`, for provider id `anthropic` unless the stored credential is `type: "api_key"` and the key starts with `sk-ant-api` (the prefix the kickoff named as a metered Console key). Today's key (`sk-ant-usr...`) is therefore not exposed, which matches ADR 0002 ("Cairn does not use it"). Anything of type `oauth`, or any value containing `sk-ant-oat`, is refused and logged by id only.
2. **Environment layer.** Pass `createModels({authContext})` with an `AuthContext.env(name)` that returns `undefined` for `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_OAUTH_TOKEN` and `ANTHROPIC_API_KEY`, and strip the same names (plus `CLAUDE_CODE_OAUTH_TOKEN`) from the brain's own `process.env` at boot. The `apiKey` auth resolver reads exactly these (section 2.8).
3. **Provider layer.** Do not register `anthropicProvider()` as is. Register a replacement with id `anthropic`: take the built-in's models and `api`, set `auth: {apiKey: guarded}` with no `oauth` entry, and wrap `stream`/`streamSimple` so a request whose `options.apiKey` contains `sk-ant-oat`, or whose headers carry a Bearer token, returns an error stream and never calls the underlying function. Until the user asks for a metered key, hide the provider from the picker altogether (`Models.getAvailable` filter), as `brain.md`'s `CairnCredentialStore` already does. A `claude-bridge/*` model never routes through this provider.
4. **Model layer.** The picker shows Claude models only under `claude-bridge`. Never alias `claude-bridge` onto `anthropic`.
5. **Judge J1** (below): seed the store with a fake `sk-ant-oat01-...` string as an `api_key`, an `oauth` credential, and each of the three env names; assert `Models.getAuth("anthropic")` is undefined, `getAvailable()` lists no `anthropic` model, a `streamSimple` call on an `anthropic` model returns an error without invoking a spy `fetch` (`ProviderRequestOptions.fetch` is injectable), and no outbound connection to `api.anthropic.com` is made (assert on the spy, and `ss -tnp` for the brain's pid in the live variant). Add an oxlint `no-restricted-imports` rule for `@earendil-works/pi-ai/auth/oauth/anthropic`, `@earendil-works/pi-ai/auth/oauth/load` and `loadAnthropicOAuth` outside `AnthropicGuard.ts`.

### 3.8 pi 1.4.0 API changes the port must absorb

- Imports: everything from `@earendil-works/pi-ai` (no pi-coding-agent, pi-tui or typebox at import time); `getBuiltinModels`/`builtinProviders` from `@earendil-works/pi-ai/providers/all` instead of `getModels` from `compat`.
- `Provider.stream*` take a `TranscriptContext`; use the transcript helpers, not `Context.systemPrompt`/`tools`.
- `createProvider`: `auth.apiKey.check(input)` is the side-effect-free probe pi uses for availability; `resolve({ctx, credential, signal})` returns `AuthResult | undefined`. Use both (dot314's `native-provider.ts` is the template).
- `StopReason` includes `pending` and `deferred`; handle `mapStopReason` accordingly. `Usage.cacheWrite1h` is new.
- `HarnessOptions.models` may be a function: build the `Models` once; the bridge's state lives in the provider closure and survives a swap. The `identity` option and `transformHeaders` do not apply.
- Compaction: pi-durable's blocking threshold, overflow recovery and the 32,768-token background compaction all apply to `claude-bridge` models unless overridden per model (`settings.compaction.modelOverrides["claude-bridge/<id>"]`, 1.4.0). See Q7 for my recommendation, which differs from `brain.md`.
- Restart limit: a generation cut off by a crash five times in a row is parked (blocked reason `restart_limit`); a bridge that crashes the brain on every attempt of the same resumed turn would trigger it. `edges.md` boot step `retryTask` handles it.
- pi-durable 1.4.0 emits `rate.?limit`-matching errors as retryable; see section 3.4 and Q6.

## 4. Risks and open questions

**Q1. Is a full-path run on 1.4.0 as good as Phase 0's numbers?** Nothing has run the bridge under pi-durable 1.4.0 with a real model yet; Phase 0 measured the SDK child only. Recommend: B0 produces the first numbers; J2 and J10 carry them into CI-style checks.

**Q2. Do the SDK-native cuts hold for Sonnet and Opus, and under real tools?** E1 to E4 are Haiku, n = 4, a trivial tool. Recommend: repeat with `claude-sonnet-5-5` and `claude-opus-5-5`, a 22K-token prefix (v1's 800-line ledger), a side-effecting tool counted out of band, and the `[1m]` ids. If any model reruns the tool, build the coherent alternative (append a real `tool_result` with cc-session-io).

**Q3. `resumeSessionAt` and `forkSession` are documented but the interplay with a killed child's late writes is not.** A killed child can flush a record into the old file. Recommend: fork after any real abort or child error; plain resume after a clean close or a brain restart (`RestartSec` is at least 2 s, S0 saw no child alive at 1 s); never write to a transcript file ourselves in slice 1.

**Q4. Session id in a stamp or in a document.** `brain.md` Q4 recommends a family document committed from provider code; I recommend the stamp (3.3). Recommend the stamp; if the user prefers a document, note that a `GenerationTask.afterResponse` hook cannot write it (hooks are read-only), so it would need `harness.commit` from provider code, outside the assistant entry's transaction, with the crash window that implies.

**Q5. One Harness per brain or per thread?** It decides how the cwd reaches the bridge (3.6). Recommend per-thread stores (`server.md` Q1) and the `beforeRequest` hook anyway, so a later move to a shared Harness does not touch the bridge.

**Q6. Retry classification.** `rate.?limit`, `429` and friends are retryable in pi-ai 1.4.0. Recommend: every error text the bridge produces for a plan window rejection starts with "Claude plan quota exceeded" (matches `quota exceeded`, which is tested first and wins), never contains an HTTP status number or the words "rate limit", "overloaded", "timeout", "terminated" or "fetch failed" unless a retry is wanted, and is built from fixed text plus a reset time. Child crashes and stalls should stay retryable (the resumed attempt is cheap). v1's comment warns that a path or other runtime value in an error text can also make pi retry or compact, so keep dynamic values out of error text. Judge: a unit test on each error constructor against `isRetryableAssistantError` and `isContextOverflow`.

**Q7. Compaction on bridge models.** `brain.md` recommends `{enabled: false, backgroundTokens: 0}` for every `claude-bridge/*` model (and its open question 7 suggests relying on Claude Code's native context). Recommend instead: keep pi compaction enabled for the blocking threshold and for overflow recovery, set only `backgroundTokens: 0`. Reasons: with `enabled: false` pi-durable has no recovery when a rebuilt or switched-in history overflows the window (overflow recovery shares the `enabled` flag, spec section 8.3); `DISABLE_AUTO_COMPACT=1` means Claude Code will not compact either; the cold cost after a pi compaction is small because the compacted context is the summary plus about 20K kept tokens, and at 1M windows a blocking compaction is rare (it needs more than 950K tokens). A speculative background compaction is the one that would force a surprise cold rebuild at 32K tokens before the limit, hence `backgroundTokens: 0`. Judge: a forced compaction on a bridge thread (small window override) yields a summary, a rebuilt Claude session, and a correct next answer; report its cache numbers rather than assert them. Also register `contextWindow` equal to what Claude Code serves: `modelUsage[model].contextWindow` from the result message tells (upstream `logServedContextWindow`); alarm on a mismatch.

**Q8. Transcript retention and a Cairn-owned `CLAUDE_CONFIG_DIR`.** Transcripts live under `~/.claude/projects/<escaped cwd>/` with the user's own sessions, appear in their `claude --resume` list, and are swept after 30 days by whichever `claude` runs first with default settings. A separate `CLAUDE_CONFIG_DIR` for the bridge's children would isolate all three problems but needs its own `claude login` (a wizard step, an extra OAuth grant on the account, still Anthropic's own flow, still no token handling by Cairn). Recommend: not in Phase 1. Use `~/.claude`, set a large `cleanupPeriodDays` in the child settings, and let the rebuild fallback cover expiry. Revisit if cache misses from sweeps show in `pi.usage`.

**Q9. SDK pin and policy drift.** Recommend: pin 0.3.305 in the catalog now; at the Phase 1 gate decide a bump to the then-latest after re-running J2, J3, J5, J6 and re-reading `https://code.claude.com/docs/en/legal-and-compliance` (research 05 section 2.7; wording changed twice in 2026). Log SDK, bundled and PATH `claude` versions at boot. Add a provider-level kill switch (config) that makes `claude-bridge` unavailable so an API key can take over if policy shifts. The experimental usage API (`usage_EXPERIMENTAL_...`) has a typed twin in 0.3.305 (`SDKControlGetUsageResponse`); treat a null as unknown.

**Q10. What is the `sk-ant-usr` key?** Only the prefix class was read. It is not `sk-ant-api` or `sk-ant-oat`. Recommend: ask the user whether it is a Console API key (and from which workspace) before Cairn ever offers an `anthropic` provider; until then the guard hides it. ADR 0002's sentence "the `anthropic` entry in the user's `auth.json` is one [a metered key]" should be softened to "is not used" in the same change that adds `AnthropicGuard`.

**Q11. Judge name collision.** `judges/bridge-orphans.sh` is S5's relay judge and uses the word the glossary reserves for the Claude provider ("Stdio relay ... Avoid: bridge"). Recommend renaming it `judges/relay-orphans.sh` in the S5 owner's next commit and naming the Claude judges `judges/claude-kill.sh`, `claude-cache.ts`, `claude-orphans.sh`, `claude-eligibility.ts`, `anthropic-oauth.test.ts`. `edges.md` item 14 reuses the cgroup method; the Claude orphan judge should reuse the same script with a different unit.

**Q12. Held tool timeouts and long approvals.** Unverified: how long Claude Code or the SDK's control channel keeps an in-process MCP call open. Recommend: explicit `timeout`, the 20-minute held-tool judge, and the watchdog excluding time in held calls.

**Q13. Tool-list changes mid-conversation.** Tools added after the query started (a deferred tool loaded by `tool_search`, an extension adding one) do not reach a held query; a changed description probably does not either (v1 brief gotcha 8, untested). Recommend: Cairn's tools for Claude are the fixed small set plus codemode, so this is rare. If the declared tool set differs from the held query's, close the query at the next tool boundary and resume natively. Judge: add a tool between turns and see it called.

**Q14. Stones.** ADR 0010 runs Claude for stones through the brain's bridge with the arms on Cloudflare. The child cwd is a scratch dir (3.6); the model sees one path in Claude Code's working-directory line and another in Cairn's sections. Recommend: state the arms path in the instructions section; test in Phase 3. Also keep the cap and the held-child TTL global across threads and stones.

**Q15. Thinking off and effort mapping.** `off` currently means Claude Code's default thinking. Recommend `thinking: {type: "disabled"}` for `off` and verify the cache effect when toggling between turns. `xhigh` maps through the model's `thinkingLevelMap` (upstream `effortForReasoning` L1132).

**Q16. Cost and attribution in the UI.** Registered model cost is zero by design (upstream `buildModels`), so `pi.usage` cost is zero and token counters are real; the plan windows are the meter. The result message's `total_cost_usd` is a list-price estimate and not evidence of charges (upstream note). Do not show it as spend.

**Q17. Images and attachments.** Claude Code accepts image blocks in a user message; the bridge passes pi's `ImageContent` through as base64 blocks and returns MCP `image` content from tools. `edges.md` says a prepared screenshot is about 2.7 MB base64 and rides every snapshot; for the bridge the concern is the resume prompt, which should never re-send an image already in the transcript. Judge: paste a screenshot, ask for the word in it, then restart and ask again.

**Q18. Packaging.** `packages/claude` versus `apps/server/src/claude/`: S6 says a package once there is a second consumer, and the judges are one. Recommend the package. The risk is lint cost: every ported file must pass type-aware oxlint with warnings failing (`!`, `any`, `typeof` and `as` are banned). Budget for that; it is the main reason to port less, which is why slice 1 drops native fork.
