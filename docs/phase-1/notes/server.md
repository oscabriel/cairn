# Phase 1 notes: the server (t3code orchestration, protocol and persistence)

Scope: what Cairn's brain must take from t3code's server side for Phase 1, and how each part maps onto pi-durable. Source of truth for ports is t3code at `fe27e8e3dc12dcbb108e9a28fd9b8cb65f34ae92` (ADR 0015). Everything below was read at that commit (a `git archive` of `packages/{contracts,provider-core,provider-pi,provider-testing,shared,client-runtime}`, `apps/server/src` and `docs/internals` into a scratch directory), pi-durable 1.4.0 from the installed package and `packages/durable/docs/spec.md` on pi's `origin/main`, Effect 4.0.5 from `node_modules/effect`, and v1's code for reference only.

## Summary

1. **Two stores, two owners.** pi-durable owns every transcript, tool call and task. Cairn's SQLite (`cairn.sqlite`) owns projects, thread rows (shell and inbox state), the shell event log, command receipts, attachments, launch intents and, per ADR 0013, nothing about approvals (they are a pi-durable document, `cairn.approvals`, in each thread's store). Every field of t3code's `OrchestrationV2ThreadShell` is either Cairn-owned state or a derived cache of pi-durable state, and the derived part is recomputed from pi-durable, never replayed.
2. **ADR 0007 is a small port.** One `RpcGroup` over `/ws`, a per-socket `RpcServer` (t3code's exact recipe, `ws.ts:3136-3270`), two streaming RPCs. `shell.subscribe` is t3code's `subscribeShell` almost verbatim (snapshot, or replay of coalesced aggregates after `afterSequence`, gap cap 1000, live tail through the budgeted buffer). `thread.subscribe` is not t3code's: it sends a `ConversationView` snapshot and then chord ops from `conversation.watch()`, every reconnect, as v1 spike 9 proved.
3. **Do not port the Orchestrator, EventSink-with-outbox, EffectWorker, ProjectionStore or the 12k-line Orchestrator.** The 12k-line `Orchestrator.ts`, the 7k-line `ProjectionStore.ts` and the provider-ingest services exist to normalize provider events into a transcript, which pi-durable already is. Port the small, reusable parts (listed in "Ports" below): `LiveStreamBudget`, `ShellStream` helpers, `ProjectCommands`, the event-store and receipt patterns, `ManagedProjectFolders`, the worktree strategy, the checkpoint recipe, the attachment signing and claim logic, the replay-transcript idea.
4. **`@effect/sql-sqlite-node@4.0.5` exists and uses `node:sqlite`** (no native build, WAL, `BEGIN IMMEDIATE`, backup, `SqliteMigrator`). Cairn does not need t3code's 1,193-line `nodeSqliteClient.ts`. Add the package to the catalog with `effect`.
5. **The harness seam is t3code's `ProviderAdapterV2` reduced to what pi-durable needs**: a scoped `open`, `submit` (idempotent by `requestId`), `interrupt`, `respond`, `configure`, a hot stream of normalized `HarnessEvent` upserts (run started and terminal, committed messages, runtime requests, usage), and the raw `watch` for the thread stream. The conformance suite is t3code's replay-transcript idea with the model as the replayed party (pi-ai's faux provider for pi-durable, direct emission for the scripted harness), asserting the normalized events and the reduced transcript.
6. **Two traps that decide the thread-stream design**: chord ops address `entries` by array index, so a bounded snapshot window needs server-side index rewriting (or a re-snapshot fallback); and entries carry base64 images and unbounded tool output, so the wire needs t3code's truncation and image-stripping projection (`WireProjection.ts`) with on-demand full reads.
7. **Worktrees, scratch project, checkpoints, attachments** port with trimming: strategy union `root | existing_worktree | worktree`, temporary branch `cairn/<8hex>` renamed by a background model call, `refs/cairn/checkpoints/<b64 threadId>/turn/<n>` captured through a scratch `GIT_INDEX_FILE`, signed one-shot raw-body uploads. PDFs reach the model as extracted text via the host's `pdftotext` (pi-ai content has only text and image blocks).
8. **Boot is the durability judge.** Threads whose runs or approvals were live must be reopened and resumed (`Harness.open`, `resume()`, `retryTask()` for parked approval waits) before the server answers `/ws`; the shell projector then recomputes derived fields. The reconnect target (within 2 s) forces a much faster client backoff than t3code's 5 minute cap.
9. **Confirmed for the client notes (`client.md` risk 12):** all of `status`, `pendingRuntimeRequest`, `latestUserMessageAt`, `lastVisitedAt`, `settledOverride`, `settledAt`, `snoozedUntil`, `pinnedAt`, `pinOrderKey`, `activeOrderKey`, `branch`, `worktreePath`, `lastErrorClass` exist in Cairn's shell row, and unseen completion is server-side via `lastVisitedAt`.
10. **Judges**: a shell-stream property test with a real socket and random drops, a `kill -9` script in the style of `spikes/3-workflows/judge.sh` that ends in a convergence check against `viewState()`, the harness conformance suite run against both harnesses, real-git tests for launch, checkpoints and diffs, attachment signing and paste-to-model timing tests, and a plain-`ws` client following the exported JSON Schema.

### Protocol: one socket, one RPC group

- **Route.** `GET /ws` is registered in `ws.ts` `layer` (3136-3270). Steps: reject with HTTP 426 `orchestration_protocol_incompatible` unless `?orchestrationProtocol=2` (`hasCompatibleOrchestrationProtocol` at 605, checked at 3148); authenticate the upgrade (`EnvironmentAuth.authenticateWebSocketUpgrade`, a session cookie or `?wsTicket=`); build `RpcServer.makeProtocolWithHttpEffectWebsocket`; run `RpcServer.make(ServerWsRpcGroup, WS_RPC_SERVER_OPTIONS)` with `Effect.forkScoped` and the per-socket handler layer; return `httpEffect`; race it against `sessions.awaitInvalidation` so revoking a session kills the socket. `WS_RPC_SERVER_OPTIONS = {disableTracing: true, disableFatalDefects: true}` (3128), with the comment that RpcServer's default would send a socket-level Defect frame that ends every pending request on the socket.
- **Server HTTP layer.** `server.ts:295-314`: `NodeHttpServer.layer(createServer, {host, port, gracefulShutdownTimeout, websocket: {perMessageDeflate: true}})`, wrapped by `rejectRequestsUntilServing` (503 until startup recovery is done) and `guardHttpResponseWriteErrors`.
- **Serialization.** `RpcSerialization.layerJson`. Client: `RpcClient.makeProtocolSocket({pingTimeout: "15 seconds", retryTransientErrors: false, retryPolicy: Schedule.recurs(0), onPingTimeout})` over `Socket.layerWebSocket` (`client-runtime/src/rpc/session.ts:208-232`, `rpc/protocol.ts:12`). Retries belong to a supervisor (`connection/supervisor.ts:41-54`: base 1 s, cap 300 s, reset after 30 s healthy, establishment timeout 15 s). "Mutations are never auto-replayed" (`docs/internals/connection-runtime.md`).
- **Orchestration RPCs** (`ORCHESTRATION_V2_WS_METHODS`, `orchestrationV2.ts:3073`): `orchestration.dispatchCommand` (unary, returns `{sequence}`), `getTurnDiff`, `getFullThreadDiff`, `searchThreads`, `searchThread`, `searchThreadStream`, `getArchivedShellSnapshot`, `getThreadProjection`, `getWorkflowScript`, `stopWorkflow`, `getTurnItem`, `launchThread`, and the streams `subscribeShell`, `subscribeThread`, `subscribeArchivedShell`, `subscribeCommandOutput`. Streaming RPCs are declared `Rpc.make(tag, {payload, success, error, stream: true})` (`rpc.ts:1721-1733`). Project, attachment and git methods are separate `WS_METHODS` entries (`projects.ensureScratch`, `projects.createNew`, `projects.searchEntries` with debounce 120 ms and limit 80 on the client, `attachments.createUploadUrl`, git and VCS methods).
- **HTTP twin** (`environmentHttp.ts:529-853`, `orchestration-v2/http.ts`): `GET /api/orchestration/shell` (the same `loadShellSnapshotParts` as the stream), `GET /api/orchestration/threads/:id` and its `/bounded`, `/history`, `/transcript` variants. The client loads the HTTP shell snapshot first, caches it (`platform/orchestrationCache.ts`, `shellCacheEncoding.ts`), then subscribes with `afterSequence: snapshotSequence`.
- **Shell stream items** (full aggregates, never diffs): `synchronized`, `snapshot {snapshot: {schemaVersion, snapshotSequence, projects, threads, archivedThreads}, resolvedRepositoryIdentityRoots?}`, `project.updated {sequence, project}`, `project.removed`, `thread.updated {sequence, location: active|archive, thread}`, `thread.removed`.
- **Thread stream items**: `synchronized`, `snapshot {snapshotSequence, projection, historyCursor?, hasMoreHistory?, latestLocalTurnOrdinal?, payloadBudgetExceeded?, turnItemsOmitLocalVisible?}`, `event {sequence, event}`, and a forward-compatible `unknown-event {sequence, eventType}` (`OrchestrationV2UnknownThreadStreamEvent`, decode-only).

### Shell resume, exactly

`ws.ts:955-1176` (`subscribeOrchestrationV2Shell`):

1. No `afterSequence`: `loadSnapshot()` runs `loadShellSnapshotParts` (one read-only transaction over threads, projects and `latestApplicationSequence`, then the threads are decoded after the transaction because the server shares one SQLite connection), then `composeShellStreamWithEnrichment({initial: snapshot items, tail: [completion marker, liveFrom(snapshotSequence)], enrichment})`.
2. With `afterSequence`: `highWater = latestApplicationSequence`; `canReplayPersistedRange(afterSequence, highWater, SHELL_RESUME_MAX_GAP = 1000)` (`ws.ts:703`, constant at 549) returns false when `highWater - afterSequence` is negative or over 1000, or when `getReplayStats` says the raw JSON payload of the range exceeds `ORCHESTRATION_REPLAY_PAYLOAD_BUDGET_BYTES = 8 MiB` (553). False means step 1.
3. Otherwise a metadata-only snapshot is sent (projects only), then `readApplicationEvents({afterSequence, throughSequence: highWater, skipUnknownEventTypes: true})` through `toShellStream`, then the completion marker, then `liveFrom(highWater)`.
4. `toShellStream` = `Stream.groupedWithin(512, 50ms)`, then per group `coalesceShellApplicationEvents` (latest event per aggregate, sorted by sequence), then refetch each aggregate's current row (`getThreadShell`, `projectService.getShell`, concurrency 8), then `skipUnchangedThreadShells`. An unchanged shell is skipped unless its last send is at least `UNCHANGED_THREAD_SHELL_RESEND_MS = 5000` old, because a skipped delta leaves the client cursor behind and a resume replays from that cursor (`ShellStream.ts`).
5. `liveFrom` = `bufferShellLiveStream(toShellStream(streamProjectedApplicationEvents({afterSequence, project: toShellApplicationEvent})))`. `streamProjectedApplicationEvents` is `replayAndBufferProjectedLiveEvents` (`LiveStreamBudget.ts:332+`): subscribe to the PubSub before reading the high-water mark, drain it into the budget, replay the database range one item at a time, then concat the live tail filtered by `sequence > throughSequence`.
6. `bufferLatestLiveStream` coalesces queued full states by key (`thread:<location>:<id>`, `project:<id>`), keeping only the highest sequence; delivered items stay charged to the budget until the client's ack. Limits: `LIVE_STREAM_MAX_ITEMS = 1000`, 8 MiB serialized (`LiveStreamBudget.ts:18-19`). Overflow fails the stream with `LiveStreamBufferError("The live event buffer is full. Resume from the last received sequence.")` and the client resubscribes.
7. Ordering after commit: `EventSink.commitThenPublish` (`EventSink.ts:253-276`) takes a single-permit `publishLane` inside the transaction and publishes after commit, so subscribers see sequences in commit order. Clients drop any item with `sequence <= snapshotSequence` (`shellReducer.ts` `applyShellStreamEvent`).
8. Client sync (`client-runtime/src/state/shell.ts:300-420`): a foreground resubscription on the same live session reuses the in-memory cursor; a new session reloads the HTTP snapshot first so a stale cursor cannot preserve incomplete cached data. Status goes `empty` to `cached` to `synchronizing` to `live`, the last on the `synchronized` marker.

Thread resume in t3code (not reused by Cairn, but the numbers are the reference): `THREAD_RESUME_MAX_REPLAY_EVENTS = 128`, 1 MiB raw and encoded (`ThreadStream.ts`), bounded snapshots of 10 user turns, 75 items, 1 MiB (`threadHistoryPaging.ts:13-18`), live coalescing 50 ms (`ThreadLiveEventCoalescer.ts`).

### Persistence in t3code

- **Event log**: `orchestration_events` (`001_OrchestrationEvents.ts`): `sequence INTEGER PRIMARY KEY AUTOINCREMENT, event_id UNIQUE, aggregate_kind, stream_id, stream_version, event_type, occurred_at, command_id, causation_event_id, correlation_id, actor_kind, payload_json, metadata_json`, unique `(aggregate_kind, stream_id, stream_version)`, plus `application_event_version` (migration `OrchestrationV2/ApplicationEventSource.ts`). Projects and threads share one sequence space, which is why one shell stream can resume everything.
- **Receipts**: `orchestration_command_receipts` (`002_...`): `command_id PRIMARY KEY, aggregate_kind, aggregate_id, accepted_at, result_sequence, status accepted|rejected, error`. `EventSink.commitCommand` (around `EventSink.ts:615-675`) reserves the receipt with `insertIfAbsent`; a duplicate command id returns the stored receipt and its events instead of re-running.
- **Atomicity**: one `sql.withTransaction` = reserve receipt, append events, apply projections, enqueue outbox effects, upsert receipt; publish after commit.
- **Outbox and worker**: `EffectOutbox.ts` (731 lines) and `EffectWorker.ts` (916): leased effects, `PROCESS_BOUND_EFFECT_TYPES` (`provider-turn.*`, `runtime-request.respond`) cancelled rather than replayed after a crash. Cairn does not need this (see "What Cairn should build").
- **Unknown rows**: reads take `skipUnknownEventTypes` only for client replay; server state building stays strict. Persisted events must stay decodable forever (`overview.md`, "Durable intent and side effects"). Migrations use `Migrator.fromRecord` with a single id space (`Migrations.ts`).
- **SQLite**: custom `NodeSqliteClient` over `node:sqlite` with reader and checkpoint worker threads (`packages/shared/src/nodeSqliteClient.ts`, 1193 lines). Pragmas in `persistence/Sqlite.ts`: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`.

### Inbox logic that is server-owned

- Commands (`orchestrationV2.ts:2562-2720`): `thread.create` (with `branch`, `worktreePath`), `thread.archive|unarchive|delete`, `thread.settle`, `thread.auto-settle {snapshotAt, settledAt?}` (rejected if the thread changed after `snapshotAt` or has any explicit override), `thread.unsettle {reason: "user"}`, `thread.snooze {snoozedUntil}`, `thread.unsnooze`, `thread.auto-settle.set {enabled}`, `thread.pin {orderKey?}`, `thread.unpin`, `thread.pin.reorder {orderKey}`, `thread.active.reorder {orderKey}`, `thread.visit {visitedAt}`, `thread.mark-unread`, `thread.metadata.update {title?, regenerateTitle?, branch?, worktreePath?, expectedBranch?, expectedWorktreePath?, expectedEmpty?}`, `thread.stop`.
- Order keys are generated by the client (`threadSort.ts` `pinOrderKeyBetween`, fractional strings) and stored by the server, which only stores them.
- Auto-settle (`ThreadSettlementService.ts`, 647 lines): `isAutoSettlementCandidate` (159) requires not archived, no explicit override, not pinned, auto-settle not disabled, no pending runtime request, no active run, no background work, no queued turn start (within a 2 minute grace), and not snoozed; `isSnoozed` (177) wakes early on failure or a pending request; inactivity rule `inactivityAtMs < now - autoSettleAfterDays * DAY_MS` (default 3 days). Merge and close rules depend on pull requests and are not needed.
- Unseen completion is `latestRunCompletedAt > lastVisitedAt`, with `thread.visit` throttled by the open thread view and `thread.mark-unread` rewinding it.

### Projects, scratch, worktrees, launch

- **Scratch** (`project/ManagedProjectFolders.ts`): `ensureScratchProject` (265) creates the project titled `"No project"` rooted at `<baseDir>/scratch` through `projects.bootstrap` with a deterministic `commandId`, catches `ProjectConflictError` to reuse the winner, and sets `projectIcon {lucide, message-square-dashed, gray}` once on creation. `folderForThread` (330) returns `<scratch>/<YYYY-MM-DD>-<first 5 words, 48 chars>-<id suffix>`, claimed with a non-recursive `mkdir` (`claimFreeFolder`: the mkdir is the claim, so racing threads cannot share a folder; fallbacks are the last 8 id characters, the full id, then a UUID suffix). Scratch is offered only when `baseDir` is outside any git work tree (probe cached, `Effect.cachedInvalidateWithTTL`). `createNamedProject` scaffolds a git repo with README and an SVG icon and removes the folder on failure.
- **Workspace resolution**: `cwd = thread.worktreePath ?? project.workspaceRoot` (`checkpointing/Utils.ts`, `project/threadWorkspaceRoot.ts`).
- **Launch** (`orchestration-v2/ThreadLaunchService.ts`, 1118 lines): `launch(input)` creates the thread immediately with a run held in `preparing`, then `prepareInBackground` does: `checkWorktreeBase` (base ref must resolve to a commit), optional fetch for `startFromOrigin`, branch naming, `git worktree add -b <branch> -- <path> <startRef>` (`GitVcsDriverCore.ts:3686-3760`, path `<worktreesDir>/<repo>/<branch with / replaced by ->`, `-c checkout.workers=...`, `GIT_PROGRESS_DELAY=0` for progress lines, submodule update per project setting), records `thread.metadata.update {branch, worktreePath}`, forks the branch rename, runs the project's `runOnWorktreeCreate` script, then releases the run (`prepared-run.release`). On failure it removes the worktree it created. Idempotence: receipts keyed by `commandId` plus derived sub-command ids (`${commandId}:workspace`, `${commandId}:branch-rename`).
- **Temporary branch** (`packages/shared/src/git.ts`): `WORKTREE_BRANCH_PREFIX = "t3"` (14), `buildTemporaryWorktreeBranchName(randomHex)` gives `t3/<8hex>` (103), `flattenTemporaryWorktreeBranchName` gives `t3-<8hex>` when a plain `t3` branch already blocks `t3/` refs (115), `isTemporaryWorktreeBranch` (123). - **Worktree cleanup** is offered on archive (`apps/web/src/worktreeCleanup.ts`); a missing managed worktree is recreated only at the path the server would choose (`worktreesDirectory.ts` `makeIsManagedWorktreePath`).

### Checkpoints

- Refs: `refs/t3/checkpoints/<Base64Url(threadId)>/turn/<n>` (`checkpointing/Utils.ts:4-10`).
- Capture is `GitVcsDriver.ts:829-1166` (research 03 said 849; the object starts at 829 and `restoreCheckpoint` at 1174). Recipe: resolve the git common dir; copy the real index to `<commondir>/t3-checkpoint-index-<uuid>` and `read-tree --reset HEAD` (or `read-tree HEAD` on a fresh scratch index when the copy is unusable), keeping the index mtime below the source's to preserve git's racy check; `-c core.fsmonitor=false -c core.splitIndex=false -c splitIndex.sharedIndexExpire=never` on every scratch-index command; seed staged-only additions when the workspace dir is ignored; `add -A -- .` (with fallback exclusions for embedded repos that have no commit); `write-tree`; `commit-tree <tree> -p HEAD -m "t3 checkpoint ref=<ref>"` with fixed author and committer; `update-ref <ref> <commit>`; always remove the scratch index. Writes use `-c core.fsync=objects,reference -c core.fsyncMethod=fsync` because unclean restarts can leave 0-byte files under `refs/t3/**` that break every fetch and push (comment at 800-813).
- `CheckpointStore` (160 lines) wraps it: `captureCheckpoint`, `hasCheckpointRef`, `restoreCheckpoint`, `diffCheckpoints {fromCheckpointRef, toCheckpointRef, ignoreWhitespace, format patch|numstat, maxOutputBytes, filePaths}`, `listAuthoredPaths` (null when HEAD did not move, else the paths the turn authored, so a `git pull` mid-turn does not credit the agent), `deleteCheckpointRefs`.
- Capture timing (`orchestration-v2/CheckpointCaptureService.ts`): at-least-once, idempotent (a settled run with a checkpoint returns), materializes baseline checkpoints for ordinals 0 and `run.ordinal - 1` when missing, then captures the run's, and commits `checkpoint.captured` plus a `checkpoint` turn item. Settled runs and the recorded provider duration are not extended by a late capture.
- Diff query (`CheckpointDiffQuery.ts`, 320 lines): `getTurnDiff {fromTurnCount, toTurnCount}` computes numstat first, batches path specs at 24,000 characters, caps output (`CHECKPOINT_DIFF_MAX_OUTPUT_BYTES`), marks `[truncated]`, filters out files the turn did not author (`isGitImport`, `Diffs.ts`). `getFullThreadDiff {toTurnCount}` is turn 0 to N.
- Revert (`CheckpointRollbackService`, `CheckpointRestoreSafety`) must coordinate with the provider conversation and rejects before touching files when the provider cannot roll back.

### Attachments

- Contract limits above. Upload (`assets/AttachmentUpload.ts`): RPC `attachments.createUploadUrl` returns `{attachmentId, relativeUrl: "/api/attachments/upload/<base64url claims>.<sig>", expiresAt}`; claims are `{version: 1, kind: "attachment-upload", type: image|file, attachmentId, name, mimeType, sizeBytes, expiresAt}` signed with an HMAC key from `ServerSecretStore` (`getOrCreateRandom("asset-access-signing-key", 32)`), validated with `timingSafeEqualBase64Url`. ### pi-durable facts that constrain the design

Read from `packages/durable/docs/spec.md` (`origin/main`) and the installed 1.4.0 `dist`:

- **Surface** (`spec.md` 2.2, 9.1-9.5): `Harness.open(storage, options, context)`, `harness.root(context, {agent})`, `harness.conversation(id, context)`, `Conversation.submit({type: "input", requestId, content, whenBusy?: steer | followUp | reject, entry?} | {type: "write", entry})`, `abort`, `agent()/configure()`, `entries(query, limit, cursor)`, `fork(at)`, `compact`, `viewState()`, `watch()`, `Harness.abortSubmission`, `abortTask`, `retryTask`, `inspect`, `watchTaskGraph`, `resume()`, `close()`. IDs (conversation, entry, task, submission) are store-assigned integers, stable across restarts, so they are "strong" provider references in t3code's terms (research 03 open question 2: answered, they work as deterministic upsert keys).
- **Views**: `ConversationView = {conversation, entries, docs}`; `entries` is the head marker followed by the non-head entries from its head (so compacted-away history is not in the view but is in storage); `docs` has `pi.agent`, `pi.live`, `pi.inbox`, `pi.provider`, `pi.usage` (spec 9.3). `watch()` delivers exact committed frames with chord ops; at most 100 pending frames, and the 101st replaces the undelivered suffix with one root replacement `[["r", newestValue]]`. "A reconnecting consumer attaches again and starts from its snapshot; nothing is replayed" (9.4). Nothing here can resume from a cursor, which is why ADR 0007 snapshots on every thread reconnect.
- **`watchEvents(harness, conversationId, context)`** is exported from the package root but "experimental... its protocol may change without notice"; it covers one conversation, buffers at most 100 batches and then replaces them with a `snapshot` event. 1.4.0 pins make it safe to use behind the seam, with conformance cases as the safety net.
- **Footguns that touch this work** (`spec.md` section 12): only the Harness appends to a busy conversation, so display-only entries must go through `submit({type: "write"})`; reads inside a commit callback hang; `watch.value` and revisions are immutable and shared, never mutate; a failed run leaves the inbox alone; fatal storage errors close the Session (isolate threads in separate stores); queued follow-ups wait until the next boundary; hook memo names collide, prefix them.
- **Crash-loop guard** (1.4.0): a task cut off 5 times in a row without progress is parked; ADR 0013 and 0012 say Cairn calls `retryTask()` at boot for tasks waiting on a pending approval and closes the Harness on SIGTERM so clean restarts never count.
- **Content types**: pi-ai `UserMessage` content has only `TextContent` and `ImageContent` (`pi-ai/dist/types.d.ts:252-270`). pi-durable ships an image processor (`@earendil-works/pi-durable/tools` exports `DEFAULT_IMAGE_LIMITS` and `ImageProcessor`; `/images/node` is the Photon worker) that v1 used at upload time.
- **Models**: pi-ai `Models.completeSimple(model, context, options)` (`models.d.ts`) is the one-shot call for titles and branch names.
- **v1 evidence** (`~/Developer/projects/cairn-v1`): `Harnesses.ts` opened one pi-durable store per thread at `<dataDir>/threads/<id>/store.sqlite` and one `Harness` per open thread, with `watch` implemented as `Stream.callback({bufferSize: 16, strategy: "suspend"})` over `root.watch()` so a slow client slows its own listener and pi-durable folds the backlog; `visible.ts` filtered hidden docs (`VISIBLE_DOCS = pi.agent, pi.live, pi.inbox, pi.usage`) from snapshots and ops; `Resume.ts` reopened every unarchived thread at boot, 8 at a time; `Http.ts` guard checked the gate header, device, and exact `Origin` on upgrades and state-changing requests; `Files.ts` content-addressed uploads with byte sniffing (png, jpeg, gif, webp, UTF-8 text) and image preparation at upload. Spike 9 numbers (`~/Developer/projects/cairn-v1/spikes/09-protocol/NOTES.md`): about 9 to 10 streaming frames a second per socket, median frame 169 bytes, a 40-turn snapshot of 260 KB decoded in 0.9 ms, reconnect to a consistent view in 102 ms including the client's 100 ms wait.
- **v2 spike evidence**: spike 4 (`spikes/4-approvals/NOTES.md`) defines `cairn.approvals` as a session document keyed by tool task id, answered by one host commit; spike 3 (`spikes/3-workflows/judge.sh`) is the template for kill scripts.

Wire details to fix now:

- **Version and negotiation**: `GET /ws?protocol=1`; an unknown value gets HTTP 426 with `{code: "protocol_incompatible", protocol: 1}` as t3code does. `session.hello` returns `{protocol, build, device, projects?, models, defaults, push?}`; the `build` id (v1: `build.json` next to the page, read on each hello) lets an open page notice a rebuilt web root.
- **Socket lifecycle** (copy t3code's shape): in the `GET /ws` handler, after the guard admits the request, build `RpcServer.makeProtocolWithHttpEffectWebsocket`, run `RpcServer.make(CairnRpcs, {disableTracing: true, disableFatalDefects: true})` with `Effect.forkScoped`, provide the handler layer for this connection, and return `httpEffect`. One server per socket means the socket's scope ends every subscription it owns.
- **Backpressure**: Effect RPC acks every chunk. The shell stream uses t3code's budget (1000 items or 8 MiB, resubscribe on overflow). The thread stream uses v1's `Stream.callback({bufferSize: 16, strategy: "suspend"})` so a slow client holds back its own `watch()` listener and pi-durable folds the backlog into one root replacement.
- **Heartbeat**: client `makeProtocolSocket({pingInterval: "3 seconds", pingTimeout: "8 seconds", retryTransientErrors: false})`. t3code's 15 s is generous for a tailnet and would eat the 2 s reconnect target after a silent drop.
- **Client supervisor**: retry delay base 250 ms, factor 2, jitter, cap 5 s, reset after 10 s healthy, plus an immediate attempt on `online`, `visibilitychange` to visible, and service-worker wake. t3code's 1 s to 300 s schedule (`supervisor.ts:41-42`) cannot meet the target. Mutations are not replayed by the transport; callers re-send with the same `commandId` or `requestId`, which makes that safe.
- **Serialization**: `RpcSerialization.layerJson` (the only one a non-Effect client can follow without a codec). The exported JSON Schema covers payloads and success values; v1's `envelope.ts` wrote the Request, Ack, Interrupt, Chunk and Exit frames as Schema so the schema document describes the whole wire. Keep that file (re-cut) and its plain-`ws` verifier.
- **Shell stream, server side**: the algorithm in "Shell resume, exactly", with these Cairn changes: thin events (no payload budget check needed, but keep the `afterSequence > highWater` snapshot case for a restored database and a new `afterSequence < earliestRetained - 1` case for pruned logs), no enrichment, one `location` (archived threads leave the stream as `thread.removed` and are read through a paged query).
- **Shell stream, client side**: snapshot (HTTP `GET /api/shell` raced with the socket, cached in `localStorage` for first paint), then `shell.subscribe({afterSequence: snapshotSequence, requestCompletionMarker: true})`, drop `sequence <= cursor`, `synchronized` flips status to `live`. After any reconnect, resubscribe with the in-memory cursor; a new page load uses the cache plus HTTP snapshot.
- **Thread stream, server side** (`threads/ThreadStream.ts`): acquire `conversation.watch(context)` inside `Stream.callback` with `Effect.acquireRelease` (stop on scope end), emit `{kind: "snapshot", seq: 0, view: visibleView(watch.value), entriesOffset, hasMoreHistory, historyCursor?}` from `watch.value`, then `watch.start(async (_v, ops) => offer({kind: "ops", seq: ++n, ops: visibleOps(ops)}))`; end or fail the stream from `watch.closed` (`stopped`/`cancelled` end it, `listener_error`/`session_failed` fail it). `seq` is per subscription and exists for tests and diagnostics; gaps cannot occur inside one ordered stream.
- **Thread stream, client side**: apply chord ops with a path-checking applier (chord's `applyImmutable` refuses `__proto__`, v1 spike 9). On reconnect, subscribe again and replace the view.
- **Identity and Origin** (ADR 0008): the guard middleware checks, before the upgrade and on every non-safe HTTP method, the exact `Origin` (403 otherwise) and the Tailscale identity from Caddy's `forward_auth` (cache `tailscale whois` by remote address for about 30 s). An open socket re-checks identity every minute like v1's `sessionEnded`, so removing the user from the tailnet kills the socket.

### Shell store and the projector (how pi-durable state reaches the inbox)

Tables in `cairn.sqlite` (`db/migrations/001..`, append-only, `Migrator`'s ledger, one id space):

- `shell_events(sequence INTEGER PRIMARY KEY AUTOINCREMENT, event_id UNIQUE, aggregate_kind 'project'|'thread', aggregate_id, event_type, occurred_at, command_id, payload_json)`; pruned to the newest 5,000 rows (AUTOINCREMENT never reuses sequences).
- `command_receipts` as above.
- `projects(id, title, workspace_root UNIQUE WHERE deleted_at IS NULL, default_model_json, default_thread_env_mode, scripts_json, kind 'folder'|'scratch'|'named', created_at, updated_at, deleted_at)`.
- `threads(id, project_id NOT NULL, title, provider, model_id, thinking_level, runtime_mode, interaction_mode, branch, worktree_path, status, created_at, updated_at, archived_at, deleted_at, settled_override, settled_at, unsettled_at, snoozed_until, snoozed_at, pinned_at, pin_order_key, active_order_key, auto_settle_disabled_at, last_visited_at, latest_run_requested_at, latest_run_started_at, latest_run_completed_at, active_run_id, activity_run_status, last_error, last_error_class, usage_limit_reset_at, pending_request_json, latest_message_json, latest_user_message_at, latest_user_authored_message_at, store_path)`: one row per thread, the projection of the shell events.
- `thread_launches(command_id PRIMARY KEY, thread_id, strategy_json, initial_message_json, attachment_ids_json, phase, error, created_at)`: the launch intent; deleted after the initial message is submitted to pi-durable (the text is held here only until then).
- `attachments(id PRIMARY KEY, thread_id NULL, name, mime, size, kind 'image'|'text'|'pdf'|'file', sha256, state 'pending'|'claimed', path, created_at, claimed_at)`.
- The upload signing key is not a table: it is a 0600 file under `<dataDir>/secrets/`.

Writers:

1. **Commands from clients** (settle, snooze, pin, visit, archive, title, project edits) go through `planThreadCommand`/`planProjectCommand` (pure, `Result`), then `EventSink.commitCommand`: one transaction with the receipt, the event, the row update, then publish after commit. A duplicate `commandId` returns the stored result. This is t3code's pattern, shrunk.
2. **Derived fields** come from `ShellProjector`, one fiber per open thread, which maps pi-durable state to a `thread.activity-updated` command with a patch (never a replay of its own events):

| Shell field | Source in pi-durable |
| --- | --- |
| `status`, `activeRunId`, `activityRunStatus`, `latestRunRequestedAt`, `latestRunStartedAt`, `latestRunCompletedAt` | `pi.live.run` present or `pi.inbox` non-empty means running (v1 `isRunning`); `run_start`/`run_end` times; a task parked by the restart limit (`TaskGraphNode.blocked: "restart_limit"`, `Harness.inspect`) adds `status: "parked"` |
| `pendingRuntimeRequest` | oldest `pending` item of the `cairn.approvals` document (Phase 2 writes it; the field and `waiting` status are in the schema from Phase 1) |
| `latestVisibleMessage`, `latestUserMessageAt`, `latestUserAuthoredMessageAt` | appended `UserEntry` (its `cairn.user` data says who wrote it: a device or another sender such as a stone) and committed `AssistantEntry` text; updated at `message_end`, never per streaming delta, so a streaming reply does not produce shell events |
| `lastError`, `lastErrorClass`, `usageLimitResetAt` | assistant entry with `stopReason: "error"` and its `errorMessage`; classification by provider adapter (the bridge reports Claude plan limits as `usage_limit` with a reset time) |
| `modelSelection`, `thinkingLevel` | Cairn row, written to `pi.agent` through `configure`; read back from the `pi.agent` document so an in-thread model change shows in the sidebar |
| `branch`, `worktreePath` | Cairn row (launch and rename) |

3. The projector debounces to one commit per 50 ms window and only commits when the derived patch differs from the row. After a restart it recomputes from the current view, so a lost event cannot leave the row wrong. A `watchEvents` `snapshot` event (backlog overflow) is just "recompute".
4. **Settlement ticker**: one fiber every 5 minutes evaluates `resolveAutoSettlementAt` for non-archived threads and commits guarded `thread.auto-settle` commands; a snooze timer wakes expired snoozes. Both are server-side so the phone and the MacBook agree.

### Thread stream: wire shape, windowing, and projection

`ThreadStreamItem = synchronized | snapshot {seq, view, entriesOffset, hasMoreHistory, historyCursor?} | ops {seq, ops}`.

- `view` is `visibleView(watch.value)`: `conversation`, `entries`, and only the docs a client may see (`pi.agent`, `pi.live`, `pi.inbox`, `pi.usage`, `cairn.approvals`; not `pi.provider`, which carries the Claude session id). `visibleOps` drops ops under hidden docs and rewrites root or `docs` replacements (v1 `visible.ts`, re-cut with tests).
- **Wire projection** (`WireEntries`): applied to snapshot entries and to ops that insert entries. (a) Replace base64 `ImageContent.data` in `model` messages and tool results with `{type: "image", attachmentRef | entryRef, mimeType, bytes}` served by `GET /api/entries/:threadId/:entryId/image/:index` (signed read, short TTL, `nosniff`); (b) truncate string payloads over 32 KiB (tool output, bash output, file bodies in tool arguments) with t3code's marker text and a `truncated: true` flag; (c) `thread.entry({threadId, entryId})` returns the full entry up to 256 KiB for expanded rows. The unwindowed spike 9 snapshot (260 KB for 80 entries) is the budget to beat.
- **Windowing**. Phase 1 starts by sending all of `view.entries` through permessage-deflate, then measures a 500-entry thread on the phone; if the snapshot exceeds the budget (proposal: 400 KB uncompressed, 1.5 s on the tailnet), switch to windows. A window is the last K user turns (t3code: 10 turns, 75 items, 1 MiB), sent with `entriesOffset = (number of leading entries elided)`. Chord ops address `entries` by absolute index, so the server rewrites: for a path `["entries", i, ...]` use `i - entriesOffset` and drop the op if `i < entriesOffset`; for the splice `["p", ["entries"], at, remove, insert]` use `at - entriesOffset` (and if `at < entriesOffset`, which only a head change causes, send a fresh `snapshot` frame instead); any root replacement becomes a new snapshot. A fresh in-stream `snapshot` is always legal, so the rewrite can give up safely.
- **History**: `thread.history({threadId, conversationId, before: EntryId, userTurns})` pages backwards with `conversation.entries({conversationId, maxEntryId: before - 1, order: "descending"}, limit, cursor)` (fork-aware, so entries compacted out of the view are still reachable), then returns them oldest first with an opaque cursor (t3code's cursor is base64 JSON `{v: 1, ...}` capped at 4,096 characters, `threadHistoryPaging.ts`). The client merges older pages before `view.entries`.
- **Subagents** (Phase 2) use the same stream with `conversationId`; the shell row of the parent carries the roll-up.

### Harness seam and conformance

Glossary: the seam is the "harness seam" (avoid "provider adapter"). Shape, in `harness/Harness.ts`:

```ts
class Harness extends Context.Service<Harness, {
  open(input: OpenThread): Effect.Effect<HarnessSession, HarnessError, Scope.Scope>
}>()("cairn/server/harness/Harness") {}

interface HarnessSession {
  readonly events: Stream.Stream<HarnessEvent, HarnessError>        // normalized, committed-only, hot
  readonly watch: Stream.Stream<ConversationFrame, HarnessError>    // snapshot then ops (thread stream)
  submit(input: TurnInput): Effect.Effect<SubmissionRef, HarnessError>   // idempotent by requestId
  interrupt(): Effect.Effect<void, HarnessError>
  respond(requestId: string, decision: ApprovalDecision, answers?: Answers): Effect.Effect<void, HarnessError>
  configure(change: AgentChange): Effect.Effect<void, HarnessError>
  history(query: HistoryQuery): Effect.Effect<HistoryPage, HarnessError>
  entry(id: EntryId): Effect.Effect<FullEntry, HarnessError>
  readonly capabilities: HarnessCapabilities                         // only flags the UI branches on
}
```

`HarnessEvent` is `ProviderAdapterV2Event` reduced to upserts with stable keys (conversation, entry, task and submission ids are strong references): `run.started {runId, inputs}`, `run.terminal {status completed|interrupted|failed, failure?: {class, retryable, resetAt?}}`, `message.committed {entryId, role, text, at}`, `runtime_request.updated {id, kind, status, summary}`, `usage.updated`, `compaction.{started,ended}`, `task.parked {taskId}`. `turn.terminal` stays the only completion signal, which the shell projector, notifications and checkpoint capture all key on.

- **`PiDurableHarness`** is the only real implementation: one `Harness` and one SQLite store per open thread (see risk 1), `submit` maps t3code's dispatch modes to `whenBusy` (`start_immediately` and `defer_start` call `submit` with the default, `steer_active` is `whenBusy: "steer"`, `queue_after_active` is `whenBusy: "followUp"`, `restart_active` is `abort` then `submit`), `queued-run.cancel` is `abortSubmission`, `interrupt` is `conversation.abort`, `events` come from `watchEvents` through `EventMapping.ts`.
- **`ScriptedHarness`** implements the same interface in memory from a transcript, with a hand-maintained `ConversationView` updated by chord's applier, so UI and server tests never need a model.
- **Transcript format** (kept from t3code's NDJSON style, with the model as the replayed party). Header `{"type": "transcript_start", "scenario": ..., "harness": ..., "version": 1}`, then entries: `input {step: message|steer|interrupt|respond|restart, text?, requestId?}`, `model {label, message}` (a pi-ai assistant message: text, thinking, tool calls, `stopReason`, `errorMessage`; the pi-durable harness feeds these to pi-ai's faux provider, `fauxAssistantMessage`/`fauxToolCall`; the scripted harness emits the equivalent entries), `tool_result {toolCallId, output}`, `crash {at}` (restart the harness over the same store), and `expect_event {event}` assertions on `HarnessEvent`s plus `expect_view {path, equals}` assertions on the reduced `ConversationView`. Scenario inputs are shared and harness-independent as in `fixtures/message_steering/input.ts`; per-harness differences are limited to how `model` entries are fed.
- **Suite**: `registerHarnessConformance(name, makeHarness)` in the style of `registerEnvConformance`; Phase 1 scenarios: `simple`, `multi_turn`, `queued_turn` (followUp), `message_steering`, `turn_interrupt`, `tool_call`, `provider_error_usage_limit`, `compaction`, `resume_after_restart`, `idempotent_resubmit` (same `requestId` twice lands once), plus `approval_*` when Phase 2 lands. The recorded t3code pi fixtures are references for shape only; they are RPC frames, not reusable.
- **Reduced transcript**: assertions read a pure reducer `foldView(ConversationView)` that the client also uses for its timeline adapter (client note risk 5), so server and client agree on what a turn is.

### Projects, threads, worktrees, launch (Cairn)

- Project commands: `project.create {projectId, title, workspaceRoot}` (workspace root must exist, be absolute, and be unique among active projects), `project.meta.update`, `project.delete` (threads keep running; the project row is soft-deleted and threads are archived by an explicit client action). Add-project UI picks a path on the Beelink via `projects.listEntries`-style directory listing (client note covers the picker).
- Scratch project: created on first need by `ensureScratchProject` with title `No project`, hidden from the project list (`kind = 'scratch'`), `projectId` never null. Per-thread folder `<dataDir>/scratch/<YYYY-MM-DD>-<words>-<id suffix>`; the thread's `cwd` is that folder; `git init` is not run for scratch folders, so checkpoints are skipped for them (non-git workspaces get no per-turn diff; show that state in the UI).
- Launch (`thread.launch` RPC, idempotent by `commandId`): in one transaction insert the thread row (`status: "preparing"`), the `thread_launches` row and a `thread.created` event; reply `{threadId, resumed}` immediately so the sidebar row appears. A launch fiber then runs `prepare`:
  1. `root`: `cwd = project.workspaceRoot` (optionally checkout `branch` is not done; `branch` is metadata like t3code's).
  2. `existing_worktree`: verify the path is a worktree of the project repo.
  3. `worktree {baseRef, branch?, startFromOrigin?}`: `checkWorktreeBase`, optional `git fetch`, temporary branch `cairn/<8hex>` unless `branch` is given, `git worktree add -b <branch> -- <path> <startRef>` at `<dataDir>/worktrees/<repo>/<branch with / as ->`, record `thread.workspace-prepared {branch, worktreePath}`; on failure remove the worktree and set `status: "failed"` with the error.
  4. Optional `runOnWorktreeCreate` project script (a supervised child process with a captured tail, no terminal manager in Phase 1).
  5. Open the pi-durable store at `store_path`, create the root conversation with `agent: {model, thinkingLevel, cwd}` (only a new root takes these), submit the initial message with `requestId = commandId`, delete the `thread_launches` row.
  6. In parallel after step 3, fork the branch rename: `Models.completeSimple` with `buildBranchNamePrompt` (cheap model from settings; deterministic slug of the first words when no model is configured or the call fails), `git branch -m` with the free-name search, then `thread.metadata.update {branch}` guarded by `expectedBranch/expectedWorktreePath`, and the same update for other threads sharing that worktree and old branch. Never blocks the run.
  Each step is idempotent and records its phase in `thread_launches`, so boot recovery resumes a launch that a `kill -9` interrupted.
- Titles: after the first user message, a forked `Models.completeSimple` with the title prompt; `thread.metadata.update {title}` (a user rename wins: guard on `titleRegeneration`/user-set flag).
- Stop/archive/delete: archive closes the session, offers worktree removal (never when dirty without confirmation), deletes checkpoint refs on delete, keeps the pi-durable store file on archive and removes it on delete.

### Checkpoints and per-turn diffs

- `git/Checkpoints.ts` captures `refs/cairn/checkpoints/<Base64Url(threadId)>/turn/<n>` with the recipe above, trimmed: copy the index into the git common dir, `read-tree --reset HEAD`, the scratch-index `-c` flags, `add -A`, `write-tree`, `commit-tree -p HEAD` (author `Cairn <cairn@localhost>`), `update-ref`, always delete the scratch index; keep the `core.fsync=objects,reference` flags; keep the embedded-repo exclusion retry; drop sparse-checkout, Windows long paths and macOS fsync branches.
- When: turn 0 baseline when the thread's first run starts (before the agent can touch files), and turn N at `run.terminal`. Capture is idempotent per `(threadId, n)`. Order and failure rules from t3code: a late capture never changes the run's recorded status or duration; a failed capture retries from the boot reconciler, not from an outbox.
- Record: a display-only transcript entry `cairn.checkpoint {turn, ref, headOid, capturedAt}` written through `submit({type: "write"})` (so the timeline can place the "changed files" card at the right row), and nothing else. The turn count is derived from the entries; no extra table. `thread.checkpointTurns` for the client comes from scanning the view for `cairn.checkpoint` entries.
- Diffs: `diff.turn {threadId, fromTurnCount, toTurnCount, ignoreWhitespace?}` and `diff.full {threadId, toTurnCount}` port t3code's `CheckpointDiffQuery`: numstat, batch path specs, cap output, `[truncated]`, filter `listAuthoredPaths`. The client renders the patch (diff viewer is the client note's area).
- Revert is not Phase 1. When it lands, reuse t3code's rule: reject before touching files if the conversation cannot be rewound (pi-durable can: `Conversation.fork(at)` or a reset head), and restore with `restoreCheckpoint`.

### Attachments end to end

1. **Create**: `attachments.createUploadUrl {name, mimeType, sizeBytes, type}` returns `{attachmentId, relativeUrl, expiresAt}`. Claims are signed with the HMAC key (32 random bytes, 0600). TTL 10 minutes. Row in `attachments` with `state: "pending"`.
2. **Upload**: `POST /api/attachments/upload/<payload>.<sig>` with the raw body; checks the Origin and identity guard, the signature and expiry, `Content-Length === sizeBytes`, streams to `.part`, sniffs the first bytes (v1 `sniff`: png, jpeg, gif, webp, UTF-8 text, PDF `%PDF-`; the declared type must agree or the upload is rejected with 415), computes sha256 while writing, renames, updates the row. 204 on success. The client starts uploads eagerly on attach, three at a time (t3code `attachmentUploadQueue.ts`), which is what makes the 2 s paste target feasible.
3. **Claim at send**: `thread.send` / `thread.launch` carry attachment ids. In one step: validate limits (`getProviderAttachmentLimitError`) and duplicates; mark `claimed` and copy the pending file to `<dataDir>/attachments/<threadId>/<id><ext>` (a copy, so a failed launch can retry; pending files older than 24 h are swept).
4. **To the model** (`AttachmentContent.ts`), returning pi-ai content blocks plus a transcript reference:
   - images: pi-durable's image processor (resize to model limits, EXIF upright) then an `ImageContent` block; HEIC is rejected with a clear message unless the client converted it (client note risk 9);
   - text and code files up to 512 KiB (v1 `MAX_TEXT_FILE_BYTES`): one `TextContent` block wrapped as `<attachment name="..." type="...">...</attachment>` (v1 `attachmentText`, whose parser lets the transcript render a chip);
   - PDFs: `pdftotext -layout -nopgbrk` (present at `/usr/bin/pdftotext`, poppler) with a 20 s timeout and a 200 KiB cap, wrapped the same way with `type="application/pdf"`; scanned PDFs yield no text, so a short note tells the model the PDF has no text layer and gives the path;
   - every attachment also gets t3code's path hint `[Attached <kind> "<name>" is saved at: <abs path>]` appended to the text (within the 120k char cap) so tools can open the file; for a stone (Phase 3) the brain copies the file into the arms before the hint is valid.
   The user entry is submitted with `entry: {kind: "cairn.user", data: {from, attachments: [{id, name, mime, size, kind}]}}` so the transcript can show chips without parsing text, and the wire projection serves images by reference.
5. **Serve back**: `GET /api/attachments/:threadId/:id` (identity guard, `nosniff`, `content-security-policy: default-src 'none'; sandbox` as v1, inline only for the sniffed image types).

### Boot, recovery and shutdown

Order in `main.ts` (the serving gate answers 503 until step 5, as `rejectRequestsUntilServing` does):

1. Acquire the one-server lock; open `cairn.sqlite` and migrate (back up the file first when a migration is pending).
2. Back up thread stores before any pi bump (ADR 0001; a pi-durable bump migrates irreversibly).
3. Decline orphan Executor approvals recorded by Phase 2 code (ADR 0013).
4. Compute the reopen set: threads with shell `status` in `preparing, running, waiting, parked`, any with an unfinished `thread_launches` row, and any whose `store.sqlite` mtime is newer than the row's `updated_at` minus a slack; plus the 20 most recently active others (cheap and bounded). Open them with concurrency 8 (`Harness.open`, `root`, `harness.resume()`, `retryTask()` for each task whose approval record is pending), each followed by one projector recompute.
5. Start the settlement ticker and open the listener. Remaining threads open lazily on first subscribe or send.
6. SIGTERM closes every Harness with a 5 s timeout so clean restarts never count toward the crash-loop guard (ADR 0012/0013), then the listener.

Idle policy: close a session 10 minutes after its last run ends with no live task, no watcher and no pending approval. v1 never closed idle sessions; N open Harnesses cost memory (to be measured, risk 1).

## Risks and open questions

1. **One pi-durable store per thread or one for all.** Recommendation: per thread, as v1 did. A Session has a single mutation line, a fatal storage error closes the whole Session (spec section 12), and the stream commits a partial reply every 100 ms, so one shared store would couple every thread's latency and failures. Cost: one open SQLite file and Harness per active thread; mitigated by the idle close policy and a reopen set. Measure RSS per open Harness before fixing the idle timeout; if it is large, add a hard cap of open sessions with LRU close of idle ones.
2. **Who owns the event log (research 03 Q1).** Answer: Cairn owns a shell event log only; transcripts are never copied. Derived shell fields are recomputed from pi-durable state, so there is no replay path that could drift.
3. **Upserts and ids (Q2).** Answer: pi-durable ids are strong, stable integers; `HarnessEvent` upserts key on them directly. A thread's root is `ROOT_CONVERSATION_ID`.
4. **Approvals (Q3).** Settled by ADR 0013: a document plus a replay-safe tool task. The shell only reads it. Risk: the approvals document lives in the thread's pi-durable store, so the sidebar cannot show a pending approval for a thread that is not open. Boot reopens threads with `waiting` status first, and the shell row keeps `pending_request_json` as a cache that survives until the projector recomputes.
5. **`watchEvents` is experimental.** Recommendation: use it behind the seam on the exact pin and cover it with conformance scenarios; keep `EventMapping` small and pure so a fallback that diffs `watch()` frames is a one-file change. Re-run conformance on every pi bump.
6. **Chord index addressing vs windowed snapshots.** Recommendation: ship full snapshots first, measure, then add the offset-and-rewrite window with a re-snapshot escape (above). Keep a test that applies windowed ops to a windowed snapshot and compares against slicing the full view.
7. **Large content on the wire** (base64 images, tool output). Recommendation: project on the wire from day one (strip images, truncate at 32 KiB, fetch on demand); without it, one pasted screenshot adds megabytes to every reconnect snapshot.
8. **Message text sits in `thread_launches` until submission.** It is pending intent, not transcript, and is deleted after the submit; acceptable under "nothing writes transcript content twice". The alternative (opening the store early and submitting once the workspace is ready) cannot work because `cwd` must exist when the root is created.
9. **Pruning the shell log.** t3code never prunes. Recommendation: keep 5,000 events and treat `afterSequence` older than the oldest retained event as a snapshot case (the gap cap of 1,000 means no live client is affected).
10. **Cold load under 1 s on the phone.** Recommendation: HTTP snapshot plus `localStorage` cache for first paint (t3code does this), WS handshake in parallel, `perMessageDeflate` on. Measure `GET /api/shell` with 300 threads; row size is about 1 KB so the budget is fine on the tailnet.
11. **Reconnect within 2 s.** t3code's supervisor cap (300 s) and ping timeout (15 s) cannot meet the target; use the schedule above and an immediate reconnect on visibility. Thread snapshots must be cheap to compute: `watch.value` is O(1) and immutable, so the cost is serialization and transfer (spike 9 measured client decode of a 260 KB snapshot at 0.9 ms and server encode only for streaming frames, 9.7 ms across 96 frames; measure snapshot encode in J8).
12. **Per-thread permission mode.** Phase 1 default is `full-access`; `runtimeMode` lives in the thread row and in the shell so the picker works, and enforcement is a Phase 2 extension that gates tools. State this in the UI so a non-default mode is not shown as protective before it is.
13. **Standards friction in ports.** S22 wants `Option` internally; t3code's shell schemas are plain nullable fields shared between the wire and reducers, and the client note ports `threadSort`/`threadInbox` that read those fields. Recommendation: keep the shell schemas on plain `NullOr` fields (they are wire payloads under S23 and the state the client reduces), convert at no boundary, and record the carve-out in `docs/coding-standards.md`. Ports from the server side (event store, sink, launch) use `Option` internally. S4 means every port is re-imported from the barrel; S8 means no `Date`.
14. **Scratch folders are not git repos**, so there are no checkpoints or diffs for "No project" threads. Recommendation: accept in Phase 1, hide the diff affordance, and let the user turn a scratch folder into a project later.
15. **Branch and title generation model.** Recommendation: a configurable cheap model resolved through `ModelRuntime` (not Claude through the bridge, which would spawn a `claude` child for a 10-token answer), default to the user's default small model, fall back to a deterministic slug.
16. **Worktree directory.** Recommendation: `<dataDir>/worktrees/<repo>/<branch>` (NVMe, ADR rule on thread stores). It is configurable later; it is not the user's `~/Developer` tree.
17. **Data directory.** Recommendation: `${XDG_DATA_HOME:-~/.local/share}/cairn` containing `cairn.sqlite`, `threads/<id>/store.sqlite`, `attachments/`, `worktrees/`, `scratch/`, `secrets/`, `backups/`. Ports: server on 127.0.0.1:3774 behind Caddy at `code.gneiss.run`.
18. **Message search** (`searchThreads`) is deferred. pi-durable has no transcript search; a Cairn FTS table would copy transcript text. Phase 1 searches titles, project names and `latestVisibleMessage` on the client.
19. **Queue editing and reorder** map poorly to pi-durable (`pi.inbox` is ordered by admission). Phase 1: show queued follow-ups from `pi.inbox`, cancel via `abortSubmission`; edit is cancel plus resubmit; drag reorder is deferred.
20. **Restart-time ordering of the serving gate.** The listener must not answer `/ws` before the reopen set is open, or a reconnecting client would converge on a view without `pi.live` and then flip. Gate on step 4 above.
21. **Executor-origin approvals and orphans** (ADR 0013) are Phase 2, but boot step 3 must exist so Phase 1 does not leave state that Phase 2 cannot clean.
22. **Two tabs, two devices.** Everything is server-owned; the only per-client state is the cursor and the draft. Concurrent `thread.visit` from two devices is last-write-wins on `lastVisitedAt` (monotonic max in the planner).
23. **Open for the user** (none blocks Phase 1; recommended answers above): whether HEIC conversion is wanted (client note); whether the checkpoint diff should also appear for scratch folders (would need `git init` in them); whether idle sessions may be closed after 10 minutes.
