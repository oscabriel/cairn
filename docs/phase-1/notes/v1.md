# Phase 1 notes: v1 code worth porting, and its lessons

Notation. `v1:` is `~/Developer/projects/cairn-v1` at `1a5cd4a56e84bfb187940428d144b584d2e084b0` (main, 31 commits, 2026-10-15 to 10-19). `v2:` is this repo at `e072229`. `up:` is an upstream repo. Line counts are from `wc -l` on that commit. Every v1 file below is a source for a port of intent, never a paste: it is re-cut to `docs/coding-standards.md` (Option instead of `undefined`, `Schema.TaggedError`, no `any` or `!`, `Clock` instead of `Date.now()`, one Effect service per plain-JS library) and starts with a header naming source repo, path and commit, plus the MIT notice where the source is MIT.

## Summary

- v1 is about 28k lines of server (`apps/server/src`: 16k top level, 5.3k in `claude/`, 6k in `sandbox/` for Docker, btrfs and cloud sandboxes that v2 does not have), 13.6k lines of web, and 16k lines of server tests. The parts that earn a port are the Claude bridge (`claude/`, 5.3k lines), the Executor client and tools (`Executor.ts`, `ExecutorTools.ts`), the Web Push sender (`webpush.ts`, `Push.ts`, `sw.js`), the attachment store (`Files.ts`), skills and context rendering (`Skills.ts`, `PiContext.ts`), usage windows (`Usage.ts`, `ClaudeUsage.ts`), the project folder rules (`Projects.ts`, `RepoIdentity.ts`), and the live judges in `apps/server/scripts/`.
- The Claude bridge is the highest-value port and the highest-risk one. The upstream `pi-claude-bridge` cannot be registered in a durable host as is (it is a pi TUI extension), and v1 already paid for the three required fixes. Port `claude/` Tier A (about 3.9k lines) and keep `rebuild.ts` as the fallback. Defer `native-fork.ts` (944 lines) until edits, rollback or compaction need it.
- v1 stores Claude Code's `session_id` as a `cairn.claude` diagnostic on the `AssistantMessage`, committed in the same transaction as the reply. That beats a separate document and passed a restart test. One gap: v1's `visibleView` filters documents only, so the stamp reaches clients inside entries. Strip it from the thread stream.
- v1's Executor client works but is over-built for v2. Keep one long-lived `McpClient` with one shared OAuth adapter (never one per call: concurrent refreshes make Executor see a reused rotated refresh token as theft), model elicitation mode, and the boot decline sweep. Drop the `mcp.json` declaration and confirm flow, the Executor-app watch and the program-always-asks machinery (Cairn's connection has no Executor app).
- v1's approvals were a `beforeTool` hook that waits on a SQLite row, with a 60 s orphan grace sweep after boot. That is the exact pattern pi-durable's spec says never to use and ADR 0013 replaces. Do not port `Approvals.ts` or `Policy.ts`. Port only `uuidv7`, the card text conventions and the Push-on-new-approval claim idea.
- Sign-in: v1's `Gate.ts` is admitted by device allowlist, refused the Beelink's own node, and spawned passkeys, a system user, unix sockets and a gate secret. Keep only its `tailscale whois` call, 30 s cache, `isIP` guard and the Origin rule from `Http.ts` `guard`. Admit by `UserProfile.LoginName` (verified on this machine: `tailscale whois --json <own ip>` returns `UserProfile.LoginName` and `Node.Tags` null for the Beelink itself).
- Attachments: v1 refuses PDFs ("attach images or text files", `apps/web/src/attachments.ts`, `apps/web/test/composer.test.ts:115-129`). There is no v1 code for PDF text. `pdftotext` and `pdftoppm` (poppler 26.08) are installed at `/usr/bin`, so PDF text is a new, small module. `Files.ts` still earns a port for byte sniffing, atomic writes and image preparation at upload; it lacks claims and garbage collection, which t3code's `AttachmentUpload.ts` and `AttachmentClaims.ts` have.
- Web Push is v1's alone (t3code at `fe27e8e3` has none). Port `webpush.ts` (RFC 8291 and 8292 on WebCrypto, no dependency), `Push.ts` (minus the approval coupling), `sw.js`, `apps/web/src/push.ts` and `webpush.test.ts` almost whole. iOS delivery to the installed PWA, locked and unlocked, was proven in v1 spike 5.
- Deployment: v1's `ops/cairn.service` plus `ops/deploy.sh` (a separate live worktree, so half-written code never reaches the phone) is the right shape. Cairn gets one loopback port, 3774, so v1's three listeners (app 3773, gate 3774, artifacts 3775) collapse to one, and `forward_auth` can give way to `reverse_proxy` with `header_up X-Cairn-Peer {remote_host}`.
- Decisions that failed and must not return: breadth before the core, a hook that waits on a person, a device allowlist, full access held to "auto-edits" on the host, Docker sandboxes with `HOME=/tmp`, `submit_result` typed as an open object (7 of 8 child results failed), opening every thread's harness at boot, shared writable `auth.json`, a 463-line `cairn.json`, and no outside judge for "like t3code".
- v1's best durable asset is its judges: `kill-test.sh`, `kill-test-claude.sh` (parked and answer cases, cache read at least 10x write), `reminder-check.ts` (a changed prompt section reaches real Claude), `follow.ts` (raw-envelope client that drops its socket mid-reply and must converge), `verify-gate.sh`, and the fake `query` and fake Executor in `apps/server/test/`.

## Facts with evidence

### F1. What v1 is and what has moved since

- v1 pinned pi 1.3.0, Effect 4.0.4, Agent SDK 0.3.301, Foldkit 0.168.0, t3code `c079503` (848 commits stale when the parity plan was written). v2 is on pi 1.4.0, Effect 4.0.5, Agent SDK 0.3.305 (spike 0), Foldkit 0.169.0, t3code `fe27e8e3`.
- v1 server layers (`v1:apps/server/src/main.ts`) form one 30-service graph; `Harnesses.ts` imports Approvals, Artifacts, Browsers, Comments, Shares, Skills, Projects, Sandboxes, Ship and more. That coupling is why nothing could be ported out of it without untangling.
- v1 tests: 60 files, 16k lines, in `v1:apps/server/test/`. The ones that matter for Phase 1: `fake-claude.ts` (105), `fake-executor.ts` (245), `claude.test.ts` (268), `claude-resume.test.ts` (303), `claude-durable.test.ts` (70), `system-reminder.test.ts` (290), `usage.test.ts` (465), `webpush.test.ts` (123), `push.test.ts` (276), `files.test.ts` (215), `skills.test.ts` (152), `executor.test.ts` (551), `executor-scope.test.ts` (185), `visible.test.ts` (39), `resume.test.ts` (128), `pi-config.test.ts` (295).

### F2. pi 1.4.0 changes that touch v1 code

From `@earendil-works/pi-durable` `CHANGELOG.md` 1.4.0 and the installed packages under `spikes/3-workflows/node_modules/@earendil-works/`:

- `defineDoc()` and `defineDocFamily()` require `checkpointWhen` on every definition. Every v1 `defineDoc` (`ChildDoc`, `ResultDoc`, the codemode store) needs it.
- `TaskRuntime.sleep()` is gone; `sleepUntil` and `ToolExecutionApi.now()` exist. A SQLite store migrates to schema 2 on open and cannot be reopened by 1.3.0, so back up every store before the bump (already in ADR 0001).
- Crash-loop guard: a task cut off 5 times in a row without a new committed state is parked (`restart_limit`). ADR 0013's boot `retryTask()` for pending approvals handles the one case that matters.
- `HarnessOptions.models` and `settings` accept functions returning the current value, so a host can swap model configuration without reopening a Harness. `HarnessOptions.identity` sets the `User-Agent` of model requests.
- `getModels` from `@earendil-works/pi-ai/compat` is deprecated; use `getBuiltinModels` from `@earendil-works/pi-ai/providers/all`. v1's `Claude.ts` `claudeModels` uses the deprecated one.
- `ModelRuntime`, `loadSkills`, `formatSkillsForPrompt`, `SettingsManager` and `DefaultPackageManager` live in `@earendil-works/pi-coding-agent`, which is not in `pnpm-workspace.yaml`'s catalog. v1 depended on it (`v1:apps/server/package.json`). `ModelRuntime.create(options)` takes `credentials?: CredentialStore`, `authPath`, `modelsPath: string | null`, `refreshOnCreate` (checked in `git show origin/main:packages/coding-agent/src/core/model-runtime.ts`, lines 110-218).
- `AssistantMessage.diagnostics?: AssistantMessageDiagnostic[]` exists in pi-ai 1.4.0 (`dist/types.d.ts:380`), which v1's session stamp relies on.
- `callers: ["tools"]` plus `root.configure({ modelTools: [codemode] }, context)` keeps a tool out of the model's list while scripts can call it (spec section 7.3; used by spike 3).

### F3. Brain and session (v1 `Harnesses.ts`, 621 lines)

- One pi-durable store per thread at `<dataDir>/threads/<id>/store.sqlite`, opened with `Harness.open(await openNodeSqliteStorage(path), { models, registry, env, settings }, context)`; `root = await harness.root(context, { agent: { model, cwd, thinkingLevel } })`; `harness.resume()` after the root exists. The one `ModelRuntime` and one `Registry` are shared across threads; per-thread extensions are added by `withThreadExtensions(base, own)` (`threadRegistry.ts`, 18 lines), which mirrors the shared registry because every thread's root is `ROOT_CONVERSATION_ID` and a shared hook cannot tell threads apart.
- `settings: { stream: { metadata: { cairnCwd } } }` is how the bridge learns each thread's working directory (pi-ai providers get no cwd).
- `Harnesses` service (shape): `open(thread)`, `close(id)`, `submit(id, { requestId, text, device, parts?, conversationId?, entry?, whenBusy? })`, `submitAndWait`, `note` (display-only entry via `type: "write"`), `abort(id, conversationId?)`, `watch(id, conversationId?) : Stream<{snapshot|ops}>`, `children`, `graph`, `statuses : SubscriptionRef<Map<id, "idle"|"running">>`. The user message is a plain string with no attachments, else text then parts (`userContent`). `entry.kind` is `cairn.user`, `data: { from: device }`.
- `watch` builds `Stream.callback` over `root.watch(context)` with `bufferSize: 16, strategy: "suspend"`, so a slow client makes pi-durable fold its backlog into one full-view frame. Status is derived from `pi.live.run` or a non-empty `pi.inbox.items` (`visible.ts` `isRunning`).
- Abort: `conversation.abort(context)` plus an explicit `claude.abortConversation(sessionId)` for the thread and for every live child it reaches through ownership (`abortReach`, `liveChildSessionIds`), because a Claude query parked at a tool call has no generation signal left.
- Shutdown: `claude.beginClosing` first (so the AbortError that `harness.close` raises is read as "closing" and the Claude session stays resumable), then `harness.close(context)` on every open entry with a 5 s timeout each.
- Boot (`main.ts` `layerResume`, `Resume.ts`): `Executor.sweep`, then `resumeAtBoot` opens every unarchived thread, 8 at a time. The opened-count and memory were never measured.
- Client-visible documents: `VISIBLE_DOCS = {pi.agent, pi.live, pi.inbox, pi.usage}` (`packages/protocol/src/view.ts`); `pi.provider` (it holds the provider session id) stays on the server. `visible.ts` `visibleView` and `visibleOps` drop other documents from snapshots and from ops (including `r` replace-root ops and `s` ops on the whole `docs` path). It does not filter entries, so `cairn.claude` diagnostics (session id and history digests) go to clients.

### F4. The Claude bridge (v1 `apps/server/src/claude/`, 5,296 lines)

Provenance (headers in each file): `pi-claude-bridge` 0.9.3 at `874fa7c2678456336f23b64e784e2057e608d83e` (Eli Dickinson, MIT) and `w-winter/dot314` `extensions/pi-claude-bridge` at `c157f4e6f9fda15b2d6698a12820e7118d19fbd7` (Warren Winter and Nico Bailon too). Both clones are on disk and still at those commits.

Why v1 ported instead of registering the package (`conversation.ts` header): upstream's `src/index.ts` is a 2,733-line pi TUI extension; v1 spike 1 loaded it through a stand-in extension API (`registerProvider`, `on(...)`) and it needed three fixes anyway: one abort signal per conversation not per generation, native resume of Claude Code's own transcript instead of rebuilding it, and the Claude Code session id stored in pi-durable. Behavior to preserve (all from code comments and spike notes):

- A fresh query per conversation, parked at every tool call; a real abort (`kill("abort")`) rotates the session (`needsRebuild`, `forceRotate`) because the killed child may still flush a record into its file; shutdown (`kill("closing")`) leaves the session resumable.
- The call is routed to a live query only if the last tool results belong to it (`pendingToolCalls`, `pendingResults`, `turnToolCallIds`); otherwise the live query is discarded and the session rebuilt.
- Compaction keeps no cache by construction: pi-durable's compacted history opens with the summary, so no prefix matches (`v1:docs/design/slice-2.md`).
- The provider is `createProvider({ id: "claude-bridge", auth: { apiKey: { resolve } } })` with no real key; `loggedIn()` refuses a turn only on a definite "none" or "third-party" login, and the model listing is stricter (first-party only), D9.
- `metadata.cairnCwd` must be an absolute path, else the default cwd.

Child RSS and time to first token (v2 spike 0, `spikes/0-bridge-numbers/NOTES.md`): about 232 MB RSS per parked child, linear to 6 children; spawn to init 198 to 261 ms; time to first token 0.94 to 2.6 s depending on model; a child exits within 2 s of its stdin closing, even if only the parent dies. No semaphore existed in v1 (it capped child conversations at 4 in `Children.ts`, not Claude queries).

### F5. Protocol (v1 `packages/protocol/src/`, 1,537 lines; v14)

- `rpc.ts` (651) is one Effect RPC group with 40-plus procedures (sandbox panes, stones, shares, terminals, workflows among them), `PROTOCOL_VERSION = 14`. `session.hello` carries the server's protocol and build ids; `apps/web/src/build.ts` reloads a stale page.
- `envelope.ts` (44) writes Effect RPC's JSON envelope (`Request`, `Ack`, `Interrupt`, `Eof`, `Ping`; `Chunk`, `Exit`, `Defect`, `Pong`) as Schema so the exported JSON Schema describes the whole wire. `view.ts` (54) has the seven chord ops (`r s d a t p m`), `Entry`, `ConversationView`, `VISIBLE_DOCS`. `attachment.ts` (51) has `Sha256`, `Attachment`, `UploadedFile`, limits (`MAX_UPLOAD_BYTES` 20 MiB, `MAX_TEXT_FILE_BYTES` 512 KiB, `MAX_ATTACHMENTS` 10) and `attachmentText`/`parseAttachmentText` (the `<attachment name=… type=…>` wrapper the transcript turns back into a chip).
- v1 had no shell stream or resume cursor: `threads.list` re-sent whole lists (a `SubscriptionRef` per service), and a reconnect took a fresh snapshot for threads. Spike 9 numbers still hold (v1 `spikes/09-protocol/NOTES.md`): about 9 to 10 frames per second while a reply streams (pi-durable commits the partial every 100 ms), median frame 169 bytes, a 40-turn snapshot 260 KB and 0.9 ms to decode, reconnect to a consistent view in 102 ms, Origin checked on the upgrade.
- `apps/server/scripts/follow.ts` is a client with no Effect code: raw envelope messages over Node's WebSocket, chord's `applyImmutable`, drops its own socket mid-reply, reconnects for a snapshot, compares with a new snapshot when idle.
- `apps/web/src/rpc.ts` (42): `RpcClient.layerProtocolSocket({ retryPolicy: Schedule.recurs(0), pingInterval })` as a Foldkit `ManagedResource`, so the Model owns reconnection (epoch bump) and `Layer.build` ties the socket to the resource scope. `backoff.ts` copies t3code's `retryDelayMs` (ceiling 30 s).

### F6. Projects and worktrees

- v1 has no git worktrees. Each thread's workspace was a btrfs snapshot (`AGENTS.md` constraint), so there is no worktree or branch-rename code to port. t3code's strategy union and temporary-branch rename come from `fe27e8e3` (`apps/server/src/git/GitManager.ts`, `checkpointing/Utils.ts`; the client note covers them).
- `Projects.ts` (582): projects live in SQLite and are added from the app; ids are folder-name slugs made unique with `-2`, `-3` and never reused (a removed row stays, softly); `scratch` is the built-in "No project" at `<dataDir>/scratch`, given an empty first commit by host git run with hooks off (`ensureScratch`); the repo identity (GitHub `owner/name`) is read once at add time from `.git/config` as a file (`RepoIdentity.ts` `readRepo`, `parseRemotes`, `selectIdentity`, `gitHubRepoOfUrl`) and kept until the user presses Re-detect; every list change happens under one lock; `threads.create` inserts under the same lock so no thread lands in a removed project.
- Folder rules (`FolderRules { home, deny, credentials }`, `checkFolder`, `addRefusal`, `browseFolder`, `MAX_ENTRIES = 500`): only under the real home directory; no dot-folders; not the home itself; not a folder inside or holding a denied path. `deny` in v1 = Cairn's data and config dirs, `~/.pi`, `~/.ssh`, `~/.claude`, `~/.config`, `~/.local/share/cairn`, `~/.alchemy`, pi's agent dir. A symlink is listed at its target only when the target is allowed. `browseFolder` returns each child's `isRepo` and GitHub identity in batches of 16.
- t3code at `fe27e8e3` has `filesystem.browse` (`apps/server/src/workspace/WorkspaceEntries.ts`, `FilesystemBrowseInput/Result` in contracts). The UI contract comes from there; v1's deny rules are the part to add.
- `sandbox/Mirror.ts` (not portable as is) has the git hygiene worth knowing for Cairn's own plumbing (checkpoint refs, per-turn diffs): a fixed `SAFE` argument list (`core.hooksPath=/dev/null`, `core.fsmonitor=false`, `gc.auto=0`), `templates.*` argument builders tested on their own, `parseRaw` for `diff-tree --raw -z`, `BlobReader` over one `cat-file --batch`, and `checkSha`/`checkBranch` validators. Its `gitEnv()` sets `HOME=/nonexistent` and `GIT_CONFIG_GLOBAL=/dev/null`, which is right for a hostile mirror and wrong for the user's own repos (signing, `safe.directory`, worktree config).

### F7. Attachments and documents

- `Files.ts` (188): a content-addressed store at `<dataDir>/files/<sha256>`. `sniff(bytes)` decides the kind from the bytes, never the client's name or type: PNG, JPEG, GIF, WebP, else strict UTF-8 text with no NUL, else refused (an `ftyp` box gets a "HEIC and video are not supported" message). Writes go to `.tmp/<uuid>` then `rename`; `.tmp` is emptied at boot. An image is "prepared" at upload (pi-durable's Photon via `@earendil-works/pi-durable/images/node` `createNodePhotonImages()`, `DEFAULT_IMAGE_LIMITS`) and the result kept as `<sha256>.image.json`, so a send never waits on image work; a failed processor start is not cached. `put` answers `{ sha256, size, mime }`; `content(attachments)` returns `TextContent | ImageContent` in order. Text goes to the model as one block wrapped by `attachmentText(name, mime, text)`.
- `Http.ts` upload and download: `POST /api/files` takes the raw body, `content-length` over `MAX_UPLOAD_BYTES` is 413, `GET /api/files/:sha256` serves with `nosniff`, `content-security-policy: default-src 'none'; sandbox`, `attachment` disposition for non-images.
- There is no PDF or document extraction, no claim step tying an upload to a thread, no expiry or garbage collection of unclaimed files, and no signed upload URL. t3code has all but extraction: `attachments.createUploadUrl` returns an HMAC-signed `/api/attachments/upload/<payload>.<sig>` valid 10 minutes (`AttachmentUpload.ts`), the client POSTs the raw body eagerly with a queue of 3 (`apps/web/src/lib/attachmentUploadQueue.ts`), `AttachmentClaims.ts` rebinds files at send, pending files expire after 24 h, and the prompt gets `[Attached … is saved at: <abs path>]` (research 03 lines 379-394; all paths exist at `fe27e8e3`).
- Web side: `apps/web/src/attachments.ts` (140) is adapted from t3code `composerAttachmentFiles.ts` at `c079503` (`classifyFile`, `shouldClaimPaste`, `admitFiles`, `shouldFoldPaste` at 8,000 chars or 200 lines, `foldedPasteName`). Re-port from `fe27e8e3`; its limits are 100 attachments, 120,000 input characters, 10 MiB per image, 80 MiB of images in total, 50 MiB per file (`packages/contracts/src/chatAttachment.ts:13-31`, checked at that commit).
- Tools available for documents on this machine: `/usr/bin/pdftotext` (poppler 26.08), `pdftoppm`, `pdfinfo`. Not installed: `pandoc`, `libreoffice`, `mutool`, `qpdf`.

### F8. Web Push, PWA and service worker

- `webpush.ts` (120): RFC 8291 `aes128gcm` and RFC 8292 VAPID with WebCrypto only. `encrypt` (ECDH P-256, HKDF with the `WebPush: info\0` key info, one record, delimiter `0x02`, record size 4096), `vapidHeader` (ES256 JWT, `aud` = endpoint origin, 12 h expiry, `sub`), `generateVapidKeys()` (public key as the uncompressed point, private key as the JWK `d`, both base64url), `sendPush(subscription, vapid, message, ttl = 3600)` with `TTL`, `Urgency: high`, 15 s timeout. It calls `Date.now()` for `exp`. `webpush.test.ts` decrypts the body with `node:crypto` (a different code path) and verifies the JWT against the `k=` key.
- `Push.ts` (292): `subscribe(device, info)` upserts by endpoint and accepts only known push hosts (`push.apple.com`, `fcm.googleapis.com`, `push.services.mozilla.com`, `notify.windows.com`, https, no port, no userinfo), so a subscription cannot aim the server's POSTs elsewhere; `deliver` retries 429, 5xx and network errors twice with doubling delay and deletes the row on 404 or 410 (only the row sent to, matched by keys); the VAPID pair is generated once into `push.json` mode 0600 with `flag: "wx"` against races; a pending approval is claimed with `UPDATE … SET notified_at = ? WHERE notified_at IS NULL` so a restart never pushes twice; the message is `{ title, body, tag, url, pending }` with `ttlFor` bounded by the approval's expiry; a second trigger fires once when Executor falls into `needsSignIn`. Subject is `mailto:admin@gneiss.run`.

### F10. Executor tools (v1 `Executor.ts` 774, `ExecutorTools.ts` 739; v2 spikes 4 and 5, `ops/executor`)

What Executor exposes, read from the live MCP endpoint (setup token, `tools/list`; nothing printed from the token): six tools `skills`, `search`, `describe`, `call`, `execute`, `resume`. `skills`, `search`, `describe` are `readOnlyHint`; `call`, `execute`, `resume` are `destructiveHint`. Input shapes: `skills {app?, name?, file?, version? ("dpl_…"), revision? (64 hex), accounts?}`; `search {query?, namespace?, limit?, offset?}`; `describe {paths: string[1..20]}`; `call {calls: {path, input} | Array<{path, input}>}` (both forms accepted; v1 sent an array of one, spike 4 an object); `execute {code ≤ 65,536 chars}`; `resume {requestId: "apr_…" | "elc_…", response: {action: "accept", content?} | {action: "decline" | "cancel"}}`. `elc_` ids are elicitation forms (`input-required`), `apr_` ids are approvals. Result statuses seen in v1: `completed`, `approval-required` (with `requestId`, `invocation {app, tool, version, kind, input, accounts}`, `elicitation.message`, `expiresAt`), `input-required`, `unavailable {reason: answered|expired|ended|not-found}`, `busy`, `capacity-exceeded`.

Client facts (v1 `Executor.ts`, spike 4 `executor.ts`, pi-mcp 1.4.0 `dist/`):

- `new McpClient({ name: "cairn", version, requestTimeoutMs: 6 min })` with `StreamableHttpTransport({ url, authProvider: adaptOAuthProvider(provider), openGetStream: false })`. Model elicitation mode is the default because the client declares no `elicitation` capability; declaring one would switch Executor to browser or client elicitation.
- `adaptOAuthProvider` keeps one `inFlight` refresh per adapter: concurrent 401s share a refresh and a request whose token was already replaced just retries ("with rotating refresh tokens, a second refresh with the old refresh token would fail and discard the new grant", `oauth/flow.js`). So one adapter must serve every session. Spike 4's `connect()` builds a fresh provider and client per call reading the grant file each time; that is safe only for one call at a time.
- `McpSessionExpiredError` means Executor restarted and lost the session and its pending approvals. v1 `lose()` drops the client, wakes waiters, and `call` resends once on a new session only for that error (Executor refused it before doing anything); any other failure after an accept was sent is "interrupted, may have run" and never retried. While anything waits, the link pings every 15 s to notice a restart.
- `CairnOAuthProvider extends McpOAuthProvider` ignores `saveCodeVerifier` and `redirectToAuthorization` unless `signingIn`, because a failed refresh mid-call runs the redirect half of the flow and would clobber a sign-in the user is in the middle of. A scoped connection's `resourceMetadataUrl` must keep the `?connection=` query (`/.well-known/oauth-protected-resource<path><search>`), else discovery yields the unscoped resource.
- The grant is `McpOAuthState` JSON in `executor_grant` row 1 bound to the exact MCP URL (a changed URL drops it). v2's grant is `~/.config/cairn/executor-grant.json` (mode 600, stored by `ops/executor/grant.ts` in the fields `serverUrl, clientInformation, tokens, tokensExpireAt`) until Cairn has a database; only one process may hold it. Access tokens last 1 h; every refresh rotates the refresh token; the revocation endpoint needs client authentication, which a public client lacks (`ops/executor/NOTES.md`).
- `Executor.sweep` at boot, before threads resume: for every approval left `pending` or `approving`, `resume decline` by `requestId`; `declineOutcome` maps `completed` to declined, `unavailable/expired` to not run, anything else to unknown; what cannot be reached within 5 s is ended locally and retried with doubling delay (5 s to 60 s) until its `expiresAt`. A late accept on the same grant would run the call (spike 3: confirmed, one row inserted).

`ExecutorTools.ts` structure: five `defineTool`s named `executor_skills`, `executor_search`, `executor_describe`, `executor_call`, `executor_execute` (`EXECUTOR_TOOL_NAMES`), all `replay: "unsafe"`; `resume` is not exposed (the model never sees a pause: the tool opens an approval, waits, calls `resume` itself, and returns only the final outcome). Scope enforcement by Cairn per call (one connection, many projects): `callRefusal` (refuses the `executor` app, apps outside `scope.apps`, and `tools.github.*` calls that do not name the project's repo via `gitHubRefusal`: every `owner` or `repo` field anywhere in the input must match, `path` and `input.path` both read, account swap refused), `canonicalPath` (resolves `tools["my-app"].x` to `my-app.x` as Executor does), `appOfPath`, result filters `filterSearch`, `filterDescribe`, `filterSkills`, `discoveryRefusal`, `executeRefusal` (a regex hint; a program can build `tools["exec"+"utor"]`, so v1 added `showsExecutorApp` and "every program asks while the connection has the Executor app"). `sameInvocation` compares canonical JSON of an approved invocation with a re-issued request, used to re-ask Executor when an approval expired before the user answered. Output is `toLlmContent(result)` from pi-mcp for non-structured results.

v2 facts that change this: Cairn's connection exposes only the GitHub app and `cairn-bridges` (convex, playwright), with the Executor app off (`ops/executor/NOTES.md`: "Search through the connection lists only the apps the connection allows (checked: Cairn bridges and GitHub, no Executor)"). Approvals are answered in the same tool call as Cairn's own approval (ADR 0013; `spikes/4-approvals/brain.ts`): `call` returns `approval-required`, Cairn records the `apr_` id in the `cairn.approvals` document, then `resume` accept at once, so Executor's 10 minute window never meets a person. Measured: `call` to approval-required 0.3 to 0.6 s including a fresh MCP connection; `resume` accept to navigation 0.27 to 0.4 s; answer commit to the waiting tool under 1 ms.

Stdio servers (`spikes/5-stdio-bridges/NOTES.md`, ADR 0014): one systemd user unit `cairn-bridges` (supergateway 4.2.0 on `172.17.0.1:3776` at `/<server>/mcp`, headless Chrome with CDP on `127.0.0.1:3775`), one hand-written Executor app (`mcpRouter`, API key in `~/.config/cairn/bridges.key` connected over the HTTP API so it is never a tool argument). Executor needs `EXECUTOR_APPS_ALLOW_PRIVATE_FETCH=true` (instance-wide), `EXECUTOR_URL_ALLOW_HTTP_ORIGINS=["http://host.docker.internal:3776"]` and a ufw `docker0` rule. Playwright marks every tool destructive, so every navigation asks. All five `kill`/`restart` events left 0 orphans (judge `judges/relay-orphans.sh`). Executor opens a new session to the relay for every discovery and call, so Cairn's tools must treat each call as stateless. `convex` runs unscoped: each call names its `projectDir`.

### F11. Sign-in, Origin and listeners

- `Gate.ts` (166): `makeDecide({ selfId, devices, whois, appHost, session })` returns allow, sign-in or refuse. - New `Documents.ts`: PDF text through `pdftotext -layout -enc UTF-8 <file> -` via `execFile` with an argument array, a page cap (for example 100 pages) and a character cap, a timeout, run in a scratch directory; `pdfinfo` for page count. If the text layer is below a threshold (a scan), render the first N pages with `pdftoppm -r 100 -png` and attach them as images through the existing image path. Text is wrapped by `attachmentText(name, mime, text)` so it is durable in the transcript and identical on every provider; a note when truncated ("showing pages 1 to 100 of 340"). ## Risks and open questions

Each has a recommended answer.

1. **Port the bridge or register the package?** Recommend port (F4). The kickoff asks to try registering first; v1 spike 1 effectively did and found three required changes plus a keyed-by-session design problem. Do not spend a day on it again; cite spike 1 in a short ADR note.
2. **How much of `claude/` to bring.** Recommend Tier A now (about 3.9k lines of the 5.3k), `native-fork.ts` and its 269-line test later. Risk: `rebuild.ts` and `native-resume.ts` depend on `cc-session-io` 0.4.0, an unofficial reader of Claude Code's session files (MIT). Pin it exactly; the SDK pin moves together with it and with the `claude` binary.
3. **Lint cost of the re-cut.** The gate rejects `any`, `!`, `typeof`, `try`/`catch` in Effect code, `Date.now()` (S8) and object parameters (`anti-slop/no-object-parameters`), all pervasive in v1's bridge. S20 relaxes assertions only inside library packages. Recommend a pilot: port `abort.ts` and `query-options.ts` into `packages/claude-bridge` and run `pnpm check` to see which rules fire before estimating. Budget the bridge as the largest single item of the phase.
4. **One pi-durable store per thread or one store.** Recommend per thread (as v1): independent backup, a bad migration or a parked task cannot take other threads down, close is per thread. Cost: open time and RSS per Harness, unmeasured. Measure with 200 stores; open lazily; boot-open only threads with unfinished work. `SqliteStorage.open(db, { prefix })` (1.3.0) would allow one file with host tables if measurements say otherwise.
5. **Where the Claude session id lives.** Recommend v1's stamp on the reply (atomic with the entry) and strip it from client views. It meets the kickoff's "store `session_id` in pi-durable".
6. **Executor connection shape.** Recommend v1's single long-lived client over spike 4's per-call client (F10): one shared `adaptOAuthProvider`, a lock so no second process holds the grant, `McpSessionExpiredError` as the only auto-resend. Judge: two threads calling Executor concurrently across a forced token refresh produce no `invalid_grant`.
7. **Approvals scope in Phase 1.** The kickoff lists approvals under Phase 2, but Phase 1's tools target hits Executor's `approval-required` immediately (playwright asks on every call). Recommend Phase 1 ships: the `cairn.approvals` document, the gated Executor tools, boot decline and `retryTask`, the approvals projection into the shell stream, the push trigger and one answer card, with permission modes full access (default) and a supervised mode for Executor calls only. Gating `bash`/`edit`/`write` in supervised modes needs a replay-safe wrapper with its own intent mark and moves to Phase 2.
8. **Code mode deadline.** A script that waits on an approval for 43 minutes (spike 4) counts that time against the sandbox deadline. Recommend `timeoutMs: Infinity` for the one shared sandbox (as spike 3), a per-call timeout inside each Executor proxy (6 minutes for a running call, the approval's own `expiresAt` for a wait), and refusing script-level `@options` deadlines.
9. **`resume` and "six tools".** The kickoff and ADR 0003 say the proxies cover six tools including `resume`; spike 4 says never expose `resume`. Recommend five proxies and update the ADR text.
10. **Semaphore semantics.** Recommend counting generating queries, not parked ones (B1). Open: what the cap does when plan windows are near full; v1 refused children past 95% (`Children.ts` `fullestWindow`); recommend a warning in the composer instead of a refusal for the user's own thread.
11. **Sign-in comparison.** The ADR says `oscabriel@`; whois returns `oscabriel@github`. Compare the full login from config. Loopback bypass (any local process can send `X-Cairn-Peer`) is accepted: such a process already runs as the user and can read the stores, which is v1's own conclusion in spike 5 decision 2 and why the system user was ceremony.
12. **Ports for dev and tests.** Only 3774 is free for Cairn; Vite dev needs a port and judges need a second instance. Recommend: Vite in middleware mode inside the dev server on 3774 (or a lease from the caddy-subdomains skill), test instances on port 0 with a temp data dir and a fake Executor (`fake-executor.ts`), never the real grant.
13. **PDF and documents.** Recommend `pdftotext` with caps and a scan fallback to images (B5). Open: whether the user needs `docx` and `xlsx` in Phase 1; recommend refusing with a clear message until asked. The kickoff's "document text reaches the model as content" is met for PDF and text.
14. **Which events push.** Recommend approvals, finished or failed turns when no visible client holds the thread, and Executor grant lapse. Open: a per-device setting; recommend none in Phase 1.
15. **`pi-coding-agent` in the catalog.** `ModelRuntime`, skills loading and settings are there; add `@earendil-works/pi-coding-agent` 1.4.0 to the catalog (it moves with the other `@earendil-works/*` packages). It is a large dependency with a TUI; the alternative is `createModels` plus a hand-written provider setup and `loadSkills` copied, which loses `models.json`, custom providers and catalog refresh. Recommend the dependency.
16. **Watching `~/.pi/agent`.** v1 re-read pi's config at thread creation and on a Reload button (the last v1 handoff left the question of a file watch open). Recommend the same: skills and context sections already render before each model request, so a watch buys little.
17. **Pi-hole and artifacts.** `*.gneiss.run` returns the LAN address, so Phase 2 portals need the v1 regex answered with the tailnet address (still live per the 2026-10-20 handoff for `a-*`/`t-*`; v2's `<port>-<stone>-pv` names need their own). Not a Phase 1 blocker.
18. **Executor upgrades.** The GitHub app health check lacks a `User-Agent` and the built-in app URL fix is by hand (`ops/executor/NOTES.md`); an Executor image bump can lose both. Recommend a smoke judge that lists tools through Cairn's grant after any bump.
