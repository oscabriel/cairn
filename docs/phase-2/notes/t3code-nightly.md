# Phase 2 notes: the t3code nightly's subagents, workflows, approvals and plans

Written 2026-10-27 as an addendum to research 03 (`~/Developer/agent-artifacts/cairn/v2/research/03-t3code.md`, frozen at `7e289ae1`), for the stage 3 planner. Everything about t3code is read at the pinned commit `fe27e8e3dc12dcbb108e9a28fd9b8cb65f34ae92` (ADR 0015) with `git -C ~/Developer/clones/github.com/pingdotgg/t3code show fe27e8e3:<path>`; the clone's working tree is at `7e289ae1`. Paths are repo-relative to t3code unless they start with `packages/bridge/`, `packages/protocol/` or `docs/decisions/`, which are Cairn's. Line numbers are at `fe27e8e3`. No Cairn code was changed.

t3code's own words are kept where they name t3code things: a "delegated task" is t3code's app-owned subagent, a "runtime request" is its approval or question record, a "proposed plan" is its plan artifact, and "provider-native" means the provider's own agent loop made it. Cairn's words follow `GLOSSARY.md`.

## Summary

1. **Nothing in these areas moved between the pins.** `git log 7e289ae1..fe27e8e3` has 12 commits; none touches `packages/contracts/src/orchestrationV2.ts`, `orchestratorMcp.ts`, `providerPolicy.ts`, `packages/client-runtime/src/state/`, `packages/provider-core/src/server/`, `packages/provider-pi/src/`, `apps/server/src/orchestration-v2/`, `docs/orchestration-v2/` or any file under `apps/web/src/components/chat/` read here. The only in-scope diff is two scheduled-task tool descriptions in `apps/server/src/mcp/toolkits/orchestrator/tools.ts` (commits `0c85b0d99`, `2ebe280e5`). Every surface below already existed at `7e289ae1`: research 03 left them out on purpose (its section 4: "Do not copy ... goals, delegated tasks"), so this is coverage, not a correction.
2. **t3code has two kinds of subagent, and Cairn has only one.** `OrchestrationV2Subagent.origin` is `provider_native` (Claude's `Agent` tool, Codex's `spawnAgent`, pi's example `subagent` extension, observed from provider events) or `app_owned` (t3code's `delegate_task` MCP tool, which the server turns into a child thread and run). In Cairn every agent runs on pi-durable (ADR 0001) and the bridge runs Claude with `tools: []` (`packages/bridge/src/ClaudeSdk.ts:427`), so no provider-native subagent, question, plan or workflow ever reaches a Cairn thread. Cairn's subagent is t3code's `app_owned` kind. Everything t3code builds only for provider-native children (`ProviderSubagentBar`, approvals asked on the parent because the provider process is the parent's, `nativeTaskRef` stop rules) is skipped.
3. **t3code's "workflow" is Claude Code's own workflow tool, not t3code's.** A Claude `local_workflow` task's `workflow_progress` snapshot (`apps/server/src/orchestration-v2/Adapters/claudeWorkflowProgress.ts:10-24`) becomes a coordinator subagent with `workflow: {name, phases, agents}` (`orchestrationV2.ts:648-695`). Its shape is close to Cairn's own workflow, which follows Claude Code workflow semantics (kickoff decision 3, ADR 0012): a script opening with `export const meta`, phases that only grow, agents with label, state, model, tokens and duration. So `WorkflowOpeningBlock` and `ThreadLineageWorkflowRow` port in behaviour, fed from Cairn's workflow journal instead of a provider snapshot.
4. **The data model is three linked records.** A child thread carries `lineage {parentThreadId, relationshipToParent: "fork" | "subagent", rootThreadId}` (`orchestrationV2.ts:108-112`); the parent's projection carries one `OrchestrationV2Subagent` per child (`:698-732`) and a `subagent` turn item in its transcript (`:1517-1528`); `subagent_spawn` and `subagent_result` context transfers record the hand-off (`:115-121`, `:181-206`). Cairn needs the lineage triple on its thread row and a subagent record per child. Context transfers are skipped: pi-durable owns the conversation and there is one harness.
5. **t3code's version of "a child asks its parent" exists, and differs from ADR 0027.** `DelegatedTaskQuestionReactor` queues a message on the parent telling its model to read the child's question with `t3_pending_request_read` and answer it with `t3_pending_request_respond`, or ask the user (`apps/server/src/orchestration-v2/DelegatedTaskQuestionReactor.ts:32-59`). It routes questions only; approvals are not routed, because the agent's tools cannot answer them (`apps/server/src/mcp/toolkits/thread/tools.ts:169-173`). The user meets a child's request through a status rolled up to the parent's sidebar row and a parent banner whose button opens the child (`apps/web/src/components/ChatView.tsx:5298-5327`). ADR 0027 instead shows what the parent cannot settle in the parent thread, answered there. Adapt: port the wake and the rollup, and replace "Open question" with a card in the parent.
6. **Approvals, questions and the plan share one composer slot.** `ChatComposer.tsx:6505-6562` shows, in priority order, the pending approval, then pending questions, then "Plan ready", in one banner above the composer. Approval actions are Decline and Approve, with Cancel and "Always allow this session" in a menu (`ComposerPendingApprovalActions.tsx:25-45`). Questions show one at a time, answered with 1 to 9 or a click, and a single-select answer advances after 200 ms (`ComposerPendingUserInputPanel.tsx:141-144`, `:163-168`). Port both; ADR 0026's brief is a new card in the same slot.
7. **The plan card depends on a plan mode Cairn does not have.** A proposed plan comes from the provider's plan mode (Claude's `ExitPlanMode`, denied and captured at `ClaudeAdapterV2.ts:8812-8829`; Codex plan items), and the composer then offers Implement, Refine and "Implement in a new thread" (`ComposerPrimaryActions.tsx:217-258`). pi has no plan item and Cairn has no interaction mode. Adapt: the brief card borrows the plan card's reading view and "Implement in a new thread" becomes "Go"; plan mode itself is skipped.
8. **Lineage lives in the Thread details side panel; subagent threads have no sidebar row.** The "Lineage" section (`ThreadRelationshipsControl.tsx:210-697`) lists the parent, forks and subagents, with running ones first, settled ones folded under "Previous agents", a stop button per running subagent and a workflow row that expands into phases. In the sidebar a subagent thread is hidden and an open one highlights its nearest non-subagent ancestor (`Sidebar.logic.ts:516-553`). Port the subagent half; skip forks and merge-back.
9. **`delegate_task` is a close template for Cairn's subagent tool.** The child gets only the task text plus an optional role (`implementation | research | review | design | test | general`), `isolation: "shared" | "worktree"`, `mode: "async" | "wait"`, a `clientRequestId` for retries, and a child permission mode that may narrow but never widen the parent's (`packages/contracts/src/orchestratorMcp.ts:134-196`; `docs/orchestration-v2/orchestrator-mcp-server.md:487-497`). Stage 4's role aliases, worktree per child and delivery tasks each have a counterpart here; the brief (ADR 0026) is what t3code lacks.
10. **"Goal" means something else in t3code.** `OrchestrationV2ThreadShell.goal` (`orchestrationV2.ts:1853`) is a provider-native `/goal` (Codex `thread/goal/*`, Claude's transcript) with an objective, status and token budget, shown as a banner with Resume and Clear (`ChatView.tsx:5391-5427`). Cairn's goal is a thread with criteria that owns subagents and stones. Skip it, and keep the word for Cairn's meaning.

What this changes in the phase 2 plan: of ADR 0011's four counterparts, subagent rows, workflow blocks and the approval and question panels port in behaviour as stated; the plan card becomes part of the brief card rather than a surface of its own. Two more counterparts exist that ADR 0011's note does not list: the Lineage panel and the child-request rollup. The steps panel (stage 4, "the look") overlaps `WorkflowOpeningBlock`'s phases and agents, so design it as that block's successor, not beside it. The stage 3 notes on subagents and delivery should read t3code's completion delivery (cohorts, generations, wake policy) before designing Cairn's delivery tasks.

Who writes what, and how it reaches the client:

- An app-owned subagent is created by the `delegated_task.request` command (`apps/server/src/orchestration-v2/Orchestrator.ts:6866`, `dispatchDelegatedTaskRequest`), which an agent's `delegate_task` call becomes. In one transaction it emits `thread.created` for the child, `node.updated` and `subagent.updated` and `turn-item.updated` on the parent (7035-7072), dispatches the task text as the child's first message (7074-7090), and records a consumed `subagent_spawn` transfer (7101-7136). The child's terminal run finalizes the subagent and writes a `subagent_result` transfer (10659-10666). Finalization reads the persisted event stream, so it also runs after a restart.
- A provider-native subagent is written by the adapter as `subagent.updated` and `turn-item.updated` upserts: Claude on its `Agent` tool (`ClaudeAdapterV2.ts:8705-8713`) and `local_workflow` tasks (`:8000`), Codex on `collabAgentToolCall` with `tool: "spawnAgent"` (`CodexAdapterV2.ts:4859`), pi on its `subagent` tool's `details.results` (`packages/provider-pi/src/server/adapter.ts:1076-1124`).
- An approval or question is written by the adapter as three upserts (runtime request, node, turn item; research 03 section 2.3). The user answers with `runtime-request.respond`; only the user does, because `t3_pending_request_respond` "cannot approve a permission request" (`apps/server/src/mcp/toolkits/thread/tools.ts:169-173`).
- The client gets the shell row (with `lineage` and `pendingRuntimeRequest`) on the shell stream, and `subagents`, `runtimeRequests`, `plans` and turn items on the thread stream. A parent's subagent rows read the child's shell for live status (`ThreadRelationshipsControl.tsx:179-208`).

### Workflows

- `resolveWorkflowOpening` (`packages/client-runtime/src/state/subagentRuntime.ts:331-361`) recognises a workflow's coordinator thread by its first user message: marked `workflowScript`, or matching `export const meta` after leading comments (295-310). It loads the parent's projection only for such a thread (368-377, `ChatView.tsx:1579-1598`).
- `WorkflowOpeningBlock` (`apps/web/src/components/chat/WorkflowOpeningBlock.tsx:38-104`) replaces that first message in the transcript (`MessagesTimeline.tsx:2150-2156`): "Workflow started", the workflow's name and description, an agent tally ("4 agents · 2 working · 1 done · 1 failed", `subagentRuntime.ts:380-422`), then each phase with "settled/total" and its member rows (106-203), then the script as highlighted JavaScript folded behind "Show full script" (205-242).
- `deriveWorkflowGroups` (`subagentRuntime.ts:235-293`) builds phases as the union of declared phases and the phases members report, because "the provider only admits a phase once something in it starts" (248-250). A phase is `pending` with no members, `running` while any member is active or idle, else `done`.
- `ThreadLineageWorkflowRow` (`apps/web/src/components/chat/ThreadLineageWorkflowRow.tsx:111-256`) is the workflow's row in the Lineage panel: the workflow's name, a hover stop button "Stop entire workflow" (144-169), and an expander listing phases (the running phase open by default, 191) with "settled/total agents", elapsed time and a "Failed" mark, then their members; "No agents yet" when empty (250). Phase labels are running, failed, stopped, done or "not started" (38-47).
- Stopping is all or nothing: `t3_workflow_stop` "Stops the whole workflow ... Individual workflow phases and agents cannot be stopped separately" (`apps/server/src/mcp/toolkits/orchestrator/tools.ts:105-115`), and the RPC fails with `not-running | unsupported | unavailable | stop-failed` (`orchestrationV2.ts:3374-3395`).

### Child questions and delivery

- `DelegatedTaskQuestionReactor` (`apps/server/src/orchestration-v2/DelegatedTaskQuestionReactor.ts`) follows the domain event stream. On a pending `user_input` request in an app-owned child, it queues a message on the parent (`dispatchMode: queue_after_active`, `createdBy: "agent"`, `creationSource: "server"`) with ids derived from the parent and request ids, so it lands once (32-59). If the request is answered or dismissed before that message starts a turn, it cancels the queued run (112-125). A parent blocked in `delegate_task` with `mode: "wait"` gets the question through the wait instead (145-156); if that wait ends early, a still-pending question wakes the parent when its run completes, fails or waits (64-101).
- Completion delivery: a terminal child wakes its parent with "Delegated task `<id>` reached a terminal state. Use task_status with taskId `<id>` to read the result." (`apps/server/src/orchestration-v2/ProviderContinuationService.ts:13-18`). `completionWake: "settled_only"` (the default) holds that wake while the parent's spawning run is live, since a blocking wait delivers the result itself (`delegated_task.request` comment at `orchestrationV2.ts:2960-2961`); results are grouped into cohorts with generations so a parent sees each result once (`OrchestrationV2DelegatedCompletionCohort`, 491-495).
- The parent's composer shows "Subagent needs approval" or "N subagents need input" with links to each child and an "Open approval" or "Open question" button (`ChatView.tsx:5298-5327`), hidden while the parent has its own pending request.

### Approvals, questions and plans in the composer

- Slot (`apps/web/src/components/chat/ChatComposer.tsx:6505-6562`): one top drawer, warning-toned for an approval, otherwise info-toned; it shows the active approval, else the first pending question, else "Plan ready" with the plan's title (`ComposerPlanFollowUpBanner.tsx:4-20`).
- Approval (`ComposerPendingApprovalPanel.tsx:11-68`): a label by kind (Command, File read, File change, App access, App permission approval), the app name, "1/N" when several wait, and the command or path in a scrollable mono block. When the provider's callback is gone it says "Provider process is gone" and the buttons disable (62-64; `canRespond` at `ChatComposer.tsx:6534`). Actions (`ComposerPendingApprovalActions.tsx:25-45`): Decline (outline) and Approve (primary) as buttons, other options in a "More approval options" menu; options with a `warning` get a warning icon and tooltip.
- Question (`ComposerPendingUserInputPanel.tsx:28-304`): the first pending request, one question at a time with "i/N"; header and question in a collapsible row; options with label, description and their digit; a check on the selected one; "Select one or more options" for multi-select; a custom answer typed into the composer; "Dismiss question without answering" when dismissible (213-228). Pure logic lives in `apps/web/src/pendingUserInput.ts` (draft answers, progress, custom answers).
- Plan card (`ProposedPlanCard.tsx:41-311`): a "Plan" badge, the plan's first heading as title, a collapsed preview with "Expand plan", and a menu with "Copy to clipboard", "Download as markdown" and "Save to workspace" (179-187). With a plan ready, the send button becomes Implement, or Refine when the draft has text, with "Implement in a new thread" in its menu (`ComposerPrimaryActions.tsx:217-258`). Implement sends "PLEASE IMPLEMENT THIS PLAN:" plus the plan in default mode; Refine sends the draft in plan mode (`apps/web/src/proposedPlan.ts:54-76`).

### Order of work this suggests

1. Schemas first (stage 4 foundations): lineage on the thread row, the subagent record, the brief as an approval payload, the question record.
2. A conformance scenario per ADR 0027 path before any UI: a child's question answered by the parent without reaching the user, and one the parent escalates, answered in the parent thread.
3. The rollup and sidebar rules, since they are pure and t3code's tests (`threadShell`, `Sidebar.logic`) are the cheapest judge.
4. Transcript rows, then the composer slot (brief, approval, question), then the Lineage panel, then the workflow block and row.

## Risks and open questions

- **Whether a parent model may answer a child's approval.** t3code forbids it (only questions route). ADR 0027 says the parent settles what it can, but ADR 0013's approval is the user's gate on a tool call. The plan must say whether a parent may decide a child's approval or only its questions; t3code's answer is "only questions".
- **Where escalated questions live.** If the card is shown in the parent but the record stays on the child, an answer from either thread must resolve the same record once. t3code avoids this by answering only in the child.
- **Workflow node stop.** t3code can stop only a whole workflow because Claude can. Cairn's nodes are durable tool tasks; stopping one node mid-script may make the replay diverge (ADR 0012). Decide before drawing a per-node stop.
- **Plan mode.** If the user wants plan mode later, the plan card returns as its own surface; until then the brief covers the "read, then Go" step.
- **The steps panel.** It overlaps the workflow block. If the design pass draws it separately, the two will show the same phases twice.
- **Parity screens.** Phase 2's screens are drawn once in the new look (ADR 0011's note), so these surfaces have no pixel baseline. Judges are behaviour scripts and the conformance suite, not `judges/parity.ts`.
